# Internationalization

Every string a user reads goes through a translation key. Literals in a component cannot be translated and cannot be reworded without a code change.

## The application's strings

`client/locales/en-US.ts` states the wording and derives the shape every other locale must match:

```ts
// client/locales/en-US.ts
import type { LocaleResource } from '@nocobase/i18n';

const enUS = {
  orders: {
    title: 'Orders',
    empty: 'No orders yet',
    count_one: '{{count}} order',
    count_other: '{{count}} orders',
  },
};

export type AppResource = LocaleResource<typeof enUS>;

export default enUS;
```

Other locales are annotated with that type, so a key you forget to translate is a compile error rather than a string that silently falls back:

```ts
// client/locales/zh-CN.ts
import type { AppResource } from './en-US.js';

const zhCN: AppResource = {
  orders: {
    title: '订单',
    empty: '暂无订单',
    count_one: '{{count}} 个订单',
    count_other: '{{count}} 个订单',
  },
};

export default zhCN;
```

Each locale is a separate dynamic import in `client/locales/index.ts`, so the browser downloads only the language it is showing. Adding a locale means adding the file and its loader entry.

## Translating in a component

```tsx
import { useTranslation } from '@nocobase/i18n/client';

export default function OrdersPage(): ReactElement {
  const { t } = useTranslation();

  return <h1>{t('orders.title')}</h1>;
}
```

No namespace argument is needed — the application's own namespace is the default in application code.

Interpolate dynamic values rather than concatenating:

```tsx
t('orders.count', { count: orders.length });
```

Keys name a meaning, not a sentence. `orders.empty` survives rewording; `orders.noOrdersYet` becomes wrong the moment the wording changes.

## Where a translation may not be mounted

A component rendered in isolation — by a focused test, for instance — may have no i18n runtime. Pass `defaultValue` so it stays readable:

```tsx
t('orders.title', { defaultValue: 'Orders' });
```

The shell components use this pattern.

## Rewording a plugin's text

Add an `overrides` block keyed by the plugin's package name to your own locale file:

```ts
const zhCN: AppResource = {
  // ...your own keys
  overrides: {
    '@nocobase/app-plugin-workflow': {
      nav: { title: '流程' },
    },
  },
};
```

Do not edit the plugin. Overrides are for product wording differences; a key or a language genuinely missing from the plugin should be fixed in the plugin.

## Language switching

`@nocobase/app-plugin-i18n` owns the language selector, persistence, and the server locale endpoints. Do not build a second selector or a parallel store.

The application shell calls `useSyncServerLocale()` so the server's messages match the language the browser is showing.

## Server-side text

API error messages and outgoing notifications need translation too, and they resolve the recipient's language rather than the browser's. A background job has no request to inherit a language from — resolve the recipient's locale explicitly and load it before translating.

## Verify

- `pnpm typecheck` passes; a missing key in a non-source locale fails it.
- The page renders correctly in both languages.
- Switching language updates the page without a reload.
- No user-visible literal remains in the component.
