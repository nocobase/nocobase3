Use the registered authorization example plugin and normal application migrations and seeds. Open `/authorization-example` for example accounts and `/authorization-example/projects`, `/authorization-example/quotes`, and `/authorization-example/orders` for independently authorized business menus. All paths are relative to the application mount.

Configure `example-sales-*` permission sets through authorization settings. Business groups contain flat resource actions. Each action declares named scopes bound to specific tables. Configure default access, sharing and restrictions by business resource, action and scopeKey. Use one `authorize` result and its `conditions.database` policies in business endpoints; generic interfaces aggregate underlying grants. Sharing records does not grant an operation or automatically share related quotes. Never copy real customer data into this example.

Scope policies are registered globally through `authz.recordAccess.add`, with generic `resources` determining applicability and DB-owned field checks narrowing built-in choices. Permission sets and all three rule editors share those choices. Projects reuse `recordsIOwn`; quote editing and submission use the independent `preparedById` through `example.sales.prepared`, while orders use parent-project ownership. Submission checks the project region independently. Page access is configured separately from business operations. Business configuration hides raw table permissions and groups resources by sales collaboration and delivery; business grants alone never allow entering a page. The inspector lists each resource’s own operations and explains both feature grants and underlying checks.

Keep four job-based permission sets: sales assistant, sales engineer, project manager and delivery specialist. Team subjects use `example.sales.team`; membership and active-state data live in the example team tables. Register membership resolution with `subjects.define(...).resolveFor` so authenticated requests and inspection agree. Seed both user and team assignments, never replace all direct assignments with team roles. Use sales_proposal and sales_dispatch to verify team-only access and sales_coordinator to verify direct-plus-inherited role union.

Use `sales_assistant`, `sales_engineer`, `sales_manager` and `sales_delivery` for direct roles. The independent team handover uses quote-7 and project-3; removing either shared scope must deny submission. Keep accepted order-source quotes separate from draft exercises. Only unrestricted administrators can reset the fixed business records through the guide's confirmation; resetting never changes authorization configuration or memberships. Restore rule changes manually before rerunning baseline exercises.

## Order relationships

The Orders page now has a relationship editor backed by the `manageRelations` business operation. Initialize the complete sales example with its single migration and seed through the application's normal migration/seed lifecycle. Use `sales_delivery` to assign/remove an active delivery team, maintain delivery checks, and manage collaborators with a join-table note. Use a read-only account to verify writes are refused. The declarations live in `server/sales-resources.ts` and use the authorization plugin's fluent relation builders; the route passes the resolved Policy to DB instead of reconstructing relation permissions. Refer to the package README for request examples. Do not grant direct foreign keys to work around a denied relation operation.

Resource declarations use `defineAuthorizationResource(name, configure)` and reusable data permissions use `defineDatabasePermission(configure)`. Both callbacks return immutable builders. Bind an action configuration key with `.grant(key, permission)`; keep page and Collection registration as `.add(...)` calls in the Provider. The portable declarations live in `server/sales-resources.ts`, and seeds use their typed resource references.

Present this as independent sales collaboration exercises, not a complete order-processing workflow. Engineers consult non-confidential reference quotes, edit their own prepared quotes and submit within their region. The Proposal team receives explicit edit and submit sharing for quote-7; withdrawing the team sharing assignment removes both capabilities. Project-8 belongs directly to sales_coordinator and stays editable after team membership or the team engineer role is revoked. Use the guide’s business exercises first and independent scope removal as an advanced check. Seeds preserve existing configuration; reset restores only seeded business records and their relations, not permission changes or user-created orders.
