# Internationalization

Every string a user reads goes through a translation key. Literals in a component cannot be translated and cannot be reworded without a code change.

## The application's strings

`client/locales/en-US.ts` states the wording and derives the shape every other locale must match:

```ts
// client/locales/en-US.ts
import type { LocaleResource } from '@nocobase/i18n';

const enUS = {
  orders: {
    title: 'Orders',
    empty: 'No orders yet',
    count_one: '{{count}} order',
    count_other: '{{count}} orders',
  },
};

export type AppResource = LocaleResource<typeof enUS>;

export default enUS;
```

Other locales are annotated with that type, so a key you forget to translate is a compile error rather than a string that silently falls back:

```ts
// client/locales/zh-CN.ts
import type { AppResource } from './en-US.js';

const zhCN: AppResource = {
  orders: {
    title: '订单',
    empty: '暂无订单',
    count_one: '{{count}} 个订单',
    count_other: '{{count}} 个订单',
  },
};

export default zhCN;
```

Each locale is a separate dynamic import in `client/locales/index.ts`, so the browser downloads only the language it is showing. Adding a locale means adding the file and its loader entry.

## Translating in a component

```tsx
import { useTranslation } from '@nocobase/i18n/client';

export default function OrdersPage(): ReactElement {
  const { t } = useTranslation();

  return <h1>{t('orders.title')}</h1>;
}
```

No namespace argument is needed — the application's own namespace is the default in application code.

Interpolate dynamic values rather than concatenating:

```tsx
t('orders.count', { count: orders.length });
```

## Naming translation keys

Use short, stable semantic names for new keys. Name the purpose of the text, not its current wording: `orders.empty` stays accurate when “No orders yet” becomes “Create your first order”. Do not use a complete English sentence as a key or turn that sentence into a long camelCase identifier.

- Use lower camelCase for each segment: `uploadFailed`, `pageDescription`. Separate feature or context groups with dots: `files.uploadFailed`, `orders.empty`. A small namespace can use a simple key such as `title`; do not add groups that convey no useful context.
- Follow the existing semantic grouping in the owning locale. Reuse an existing key only when its meaning and translation context match. For example, an “Open” action and an “Open” status need distinct keys even when their English values match.
- Keep package names in the namespace, not in every key. Application text belongs to the application namespace; plugin text belongs to the plugin namespace.
- Keep variables in values and pass them as interpolation options. Use i18next plural suffixes such as `_one` and `_other` when needed; these suffixes are exceptions to camelCase.
- Keep the key when only wording changes. When renaming a key, update every locale, translation call, navigation/breadcrumb title, and dynamic lookup that uses it together. Do not rename unrelated existing keys just to match a new convention.

| Purpose                | Prefer                                         | Avoid                                |
| ---------------------- | ---------------------------------------------- | ------------------------------------ |
| Order page heading     | `orders.title`                                 | `Order list`                         |
| Empty order list       | `orders.empty`                                 | `orders.noOrdersHaveBeenCreatedYet`  |
| Upload error           | `files.uploadFailed`                           | `File upload failed.`                |
| Demo explanation       | `demo.pageDescription`                         | `This page demonstrates the plugin.` |
| Two meanings of “Open” | `actions.open`, `status.open`                  | One shared `open` key for both       |
| Selected item count    | `selection.count_one`, `selection.count_other` | A key containing the current count   |

For example, define a group in `en-US.ts` and mirror it in the other locales:

```ts
const enUS = {
  selection: {
    count_one: '{{count}} item selected',
    count_other: '{{count}} items selected',
  },
  files: {
    uploadFailed: 'Could not upload {{name}}.',
  },
};
```

```tsx
t('selection.count', { count: selectedItems.length });
t('files.uploadFailed', { name: file.name });
```

Prefer nested objects for new groups; existing flat dotted keys need not be restructured solely for this convention. Type checking verifies locale shape, not naming quality: review key names against these rules as well.

## Where a translation may not be mounted

A component rendered in isolation — by a focused test, for instance — may have no i18n runtime. Pass `defaultValue` so it stays readable:

```tsx
t('orders.title', { defaultValue: 'Orders' });
```

The shell components use this pattern.

## Rewording a plugin's text

Add an `overrides` block keyed by the plugin's package name to your own locale file:

```ts
const zhCN: AppResource = {
  // ...your own keys
  overrides: {
    '@nocobase/app-plugin-workflow': {
      nav: { title: '流程' },
    },
  },
};
```

Do not edit the plugin. Overrides are for product wording differences; a key or a language genuinely missing from the plugin should be fixed in the plugin.

## Language switching

`@nocobase/app-plugin-i18n` owns the language selector, persistence, and the server locale endpoints. Do not build a second selector or a parallel store.

The application shell calls `useSyncServerLocale()` so server messages use the browser's language when the server supports it. If the server does not have that locale, the browser still switches and the server uses English; the language control shows an informational notice about the fallback.

## Server-side text

API error messages and outgoing notifications need translation too, and they resolve the recipient's language rather than the browser's. A background job has no request to inherit a language from — resolve the recipient's locale explicitly and load it before translating.

## Verify

- `pnpm typecheck` passes; a missing key in a non-source locale fails it.
- `pnpm nocobase app i18n:check` reports any language declared on only one of the two sides and exits nonzero until the lists align; add the missing side when it needs translated text.
- The page renders correctly in both languages.
- Switching language updates the page without a reload.
- No user-visible literal remains in the component.

## Which languages the application offers

The application's own locale files are the list. `client/locales/index.ts` decides what the browser offers and `server/locales/index.ts` what the server does, so adding a language means adding its file and loader entry on the side that needs it — there is no configured list to keep in step.

A plugin's locale file supplies translations for those languages, never a new one. A plugin shipping `ja-JP` to an application that does not offer Japanese puts nothing in the picker. Prefer keeping the client and server lists aligned when server-produced text needs the language. A client-only language is also valid: the interface switches to it, `POST /api/i18n/locale` records English for the server, and the language control explains the fallback with an informational notice.

## Default language

`i18n.defaultLocale` in `config.yml` names the language the application starts in, for the browser and the server alike:

```yaml
i18n:
  defaultLocale: zh-CN
```

It defaults to `en-US`, and `APP_DEFAULT_LOCALE` overrides it. A value the application does not translate is ignored on the client and falls back on every key on the server.

The browser resolves its startup language as: the visitor's saved choice in `localStorage` → `i18n.defaultLocale` → `en-US`. The browser's own `navigator.language` is deliberately not consulted — the language an application starts in is the product's decision, not the visitor's operating system's. A default is never written to storage as though the visitor had chosen it, so changing configuration still reaches anyone who has not picked a language. Refresh after changing it.

Switching language in the interface remains a user-level choice: it writes `localStorage` and the server session, and never changes `defaultLocale`.

## What an untranslated key falls back to

A key missing from the language in use is looked up in `i18n.defaultLocale`, and then in `en-US`:

```text
the language in use  →  i18n.defaultLocale  →  en-US
```

The second step is what an application adding a language its plugins have not translated relies on. An application defaulting to `zh-CN` that adds `es-ES` leaves a plugin with neither, and English is the one language that plugin almost certainly ships — a Spanish speaker reading English is a worse result than reading Spanish, and a better one than reading Chinese.
