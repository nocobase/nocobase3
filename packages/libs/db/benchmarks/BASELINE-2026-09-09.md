# 五库数字处理性能基线（2026-09-09）

本轮只增加 benchmark、测量工具自测和开发命令，没有修改运行时代码。先保留现状的可复现数据，再决定 SQL 和元数据处理的优化。

## 方法与范围

- 环境：Node v24.15.0，Apple M3 Max，darwin/arm64。四个远程数据库运行在本机 Docker，SQLite 使用内存库。
- 正式基线：五库 × 两档输入（10,000 / 100,000 行）× 45 组场景，共 450 组；每组预热 2 次、测量 5 次。
- 正式基线采集后增加了 2 组 SQL 控制场景；当前默认命令每档每库执行 47 组（五库两档共 470 组），本摘要的 450 组指当时完整采集的正式场景。
- SQL 结构对照：五库 × 8 组，共 40 组；每组预热 2 次、测量 7 次。总计 2,530 个计时样本。
- 全部场景完成，无跳过。整数、DECIMAL、读取和写入结果严格验证；浮点聚合验证有限值，并记录其数学误差。耗时为中位数，单位 ms。
- 原生 Knex 与 Query/Repository 使用同一个连接客户端和当前驱动转换配置；不是对旧版本运行时的回归对比，也没有隔离驱动转换的独立成本。
- API 固定顺序、只有一个连接、没有并发业务负载；结果不代表生产吞吐量或跨机器数据库排名。MySQL 创建场景保留原有 RETURNING 警告输出，其成本包含在计时中。
- 原始数据包含每次采样、SQL 模板和频次、Node CPU、内存差值、单次事件循环探针、实际聚合误差、数据库/驱动版本和运行时源码哈希。

## 1. DECIMAL SUM + AVG：SQLite 最值得优化

输入 100,000 行，每次执行同时计算 SUM 和 AVG，各入口均执行一个 SQL Query 事件。

| 数据库   | 原生 Knex | Query | Repository | Query / 原生 |
| -------- | --------: | ----: | ---------: | -----------: |
| sqlite   |      3.54 | 50.03 |      50.09 |       14.11× |
| postgres |      5.27 |  8.23 |       8.21 |        1.56× |
| mysql    |     11.44 | 12.07 |      12.34 |        1.06× |
| oracle   |      3.43 |  3.70 |       3.45 |        1.08× |
| mssql    |     28.73 | 32.41 |      32.46 |        1.13× |

SQLite 还测试了 10,000 个分组的 SUM 后排序：原生约 15.21 ms，Query 约 115.04 ms，Repository 约 129.07 ms。Query 的单次 setImmediate 延迟约 115.09 ms，说明同步聚合会占用当前 Node 线程。该比较包含自定义聚合、精确排序键与结果解码，尚未分别归因。

## 2. DECIMAL 创建：额外读回可直接数出来

每次 createMany 创建并返回 1,000 条记录，以下取 100,000 行规模这一轮的独立写表结果。SQL 次数是 Knex Query 事件，包含可见事务命令，不等于网络包数量。

| 数据库   | INTEGER ms | DECIMAL ms | INTEGER SQL | DECIMAL SQL | 额外 SQL |
| -------- | ---------: | ---------: | ----------: | ----------: | -------: |
| sqlite   |      45.97 |      79.76 |        2002 |        3002 |     1000 |
| postgres |     967.74 |    1475.16 |        2002 |        3002 |     1000 |
| mysql    |    1477.90 |    1505.59 |        3002 |        3002 |        0 |
| oracle   |    1145.10 |    1698.48 |        2000 |        3000 |     1000 |
| mssql    |    1830.63 |    2849.75 |        2000 |        3000 |     1000 |

除 MySQL 外，DECIMAL 每条多一次读回。MySQL 两种字段原本均走读回路径。Oracle/SQL Server 的事务控制不一定以 Knex query 事件出现，不能把不同库的绝对事件数直接当作事务次数差异。

## 3. Query 冷元数据：额外 Schema 查询确实存在

查询 100 条 INTEGER 字段，缓存只失效指定 Collection，连接、命名索引和数据库页缓存不刻意清空。

| 数据库   | 热缓存 ms / SQL | 冷缓存 ms / SQL |
| -------- | --------------- | --------------- |
| sqlite   | 0.18 / 1        | 0.31 / 6        |
| postgres | 0.65 / 1        | 4.59 / 5        |
| mysql    | 0.90 / 1        | 5.96 / 7        |
| oracle   | 1.74 / 1        | 34.83 / 8       |
| mssql    | 0.87 / 1        | 8.89 / 8        |

本轮使用内存补充元数据存储；生产环境使用数据库元数据存储时，冷加载成本可能不同。暖缓存额外 SQL 为零，但仍包含字段查找和复制。这里只投影 INTEGER 的源表也包含 DECIMAL，不能代表“完全没有 DECIMAL 的集合”所有路径。

## 4. COUNT：先看 SQL 投影，不能直接归因于 JS 范围检查

以下来自独立 7 次重复对照；“原生 + 投影”使用与公共 API 相同的 COUNT 聚合及外层文本投影，但不经过 Query/Repository 解码。

| 数据库   | 原生 COUNT | 原生 + 投影 | Query COUNT | Repository COUNT |
| -------- | ---------: | ----------: | ----------: | ---------------: |
| sqlite   |       0.06 |        0.55 |        0.68 |             0.64 |
| postgres |       3.47 |        3.22 |        3.52 |             3.68 |
| mysql    |       2.77 |        6.63 |        6.67 |             6.80 |
| oracle   |       1.71 |        2.42 |        1.83 |             2.23 |
| mssql    |       7.96 |        8.10 |        8.60 |             7.91 |

SQLite/MySQL 的投影对照接近公共 API 耗时，说明主要差距可在 SQL 层复现。尚未采集 EXPLAIN，不能断言具体是哪种优化被禁用。PostgreSQL、Oracle、SQL Server 的小差值不足以作为稳定百分比结论。

## 5. Repository 分页：空值排序表达式是另一个 SQL 成本

整数主键分页返回 100 条。原生对照仅补上 `ORDER BY CASE WHEN id IS NULL THEN 1 ELSE 0 END, id`，保留相同筛选和分页。

| 数据库   | 原生简单排序 | 原生空值排序 | Repository |
| -------- | -----------: | -----------: | ---------: |
| sqlite   |         0.11 |         3.49 |       3.69 |
| postgres |         0.68 |        10.37 |      10.96 |
| mysql    |         0.74 |         0.68 |       0.99 |
| oracle   |         2.44 |         7.62 |       7.78 |
| mssql    |         1.14 |        12.02 |      11.49 |

SQLite、PostgreSQL、Oracle 和 SQL Server 的较大分页差距可由空值排序 SQL 复现。这不是本轮新引入的代码修改，也不能把整个 Repository/Knex 差值当作数字解码开销。建议后续检查非空字段是否仍需此表达式，并用执行计划验证。

## 精度观察

- PostgreSQL FLOAT（real）与 Oracle BINARY_FLOAT 在 100,000 行 `.25` 数据上，SUM 期望 4,975,000，实际 4,971,082，约 -0.078754%。本轮公共 API 保留了该误差；返回字符串不代表修复浮点累计误差。
- Oracle FLOAT 的 AVG 也有约 -0.03918 误差。PostgreSQL 的当前 AVG 转 numeric 后此次结果准确，但成本高于原生浮点 AVG。
- SQL Server 原生 AVG(integer) 得到 49，公共 API 得到字符串 49.5。两者耗时不能在忽略语义差异的前提下解释。
- 基准不承诺任意精度浮点聚合正确；具体误差保存在 accuracy 和 resultPreview。

## 下一步建议

1. 优先减少 DECIMAL 创建的逐记录额外读回，保持返回精度与事务语义。
2. 优化 SQLite 精确 SUM/AVG 的逐行解析、BigInt 累加和排序键，并用现有精度测试守住行为。
3. 检查 SQLite/MySQL COUNT 的结果投影能否使用不改变计数优化的安全传输方式；不要先微调 JS 正则。
4. 单独评估非空字段排序 SQL 和 Query Collection 依赖。冷缓存 SQL 已有基线；缓存命中复制成本仍需专项归因。
