# Repository V1.1 roadmap

Each stage includes implementation, public types, tests, documentation, package checks, and an independent commit before the next stage starts.

| Stage | Capability                                               | Status   |
| ----- | -------------------------------------------------------- | -------- |
| 1     | Numeric atomic updates, Builder and JSON                 | Complete |
| 2     | Cursor `direction`, root and relation-local              | Complete |
| 3     | Case-insensitive string filters                          | Complete |
| 4     | JSON and JSON-array filters                              | Complete |
| 5     | Relation aggregates and independent `combine()` branches | Complete |
| 6     | Explicit belongsToMany junction payloads                 | Pending  |

`findOne()` retains its current semantics. Relation aggregate selection uses `include()` and `combine()`, with no `select.aggregate()` entry. Arrays in stage 4 mean JSON arrays, not native database array fields. Relation-local offset and Streaming relation includes remain outside this iteration.

## Numeric atomic updates

```ts
await accounts.updateOne({
  filter: { id: 'account-1' },
  values: {
    balance: (value) => value.increment('100.25'),
    loginCount: { increment: 1 },
  },
});
```

Supported operations are `increment`, `decrement`, `multiply`, and `divide`. Direct values remain assignments. Updates run as database expressions and preserve SQL NULL. Numeric strings preserve input precision; integer fields require exact integer operands. Division by zero is rejected. Division and assignment follow the database's numeric type rules: integer division can truncate or round depending on the dialect. Use decimal fields when fractional results are required. Decimal precision and overflow remain governed by the declared database type.

Atomic operations apply to updateOne, updateMany, and root/nested upsert update branches. Creation rejects them. Generated, optimistic-lock, primary-key, and unique identity fields cannot use atomic expressions. JSON objects remain literal data, even when they contain operation names. Runtime Collection metadata determines which operations a dynamically typed field permits.

## JSON filters

```ts
filter: (filter) =>
  filter.and([
    filter.json('metadata').path(['profile', 'country']).eq('CN'),
    filter.json('metadata').path(['tags']).hasEvery(['database', 'orm']),
  ]);
```

JSON supports structural `eq`/`ne`, scalar array membership `has`, `hasSome`,
`hasEvery`, array `isEmpty`/`isNotEmpty`, and `isDbNull`, `isJsonNull`,
`isAnyNull`. Object key order does not matter; array order and element types do.
`hasEvery([])` matches arrays, including empty arrays; `hasSome([])` matches
nothing. Missing paths match none of the null operators. `isAnyNull()` matches
SQL NULL columns or JSON null at the selected path. `isDbNull()` only accepts
whole columns. Paths use non-empty string keys or non-negative integer indexes;
keys containing quotes, backslashes, or NUL are rejected in this version.

The JSON AST uses `operator: '$jsonEq'` (or the corresponding `$jsonHas`,
`$jsonHasSome`, `$jsonHasEvery`, `$jsonEmpty`, `$jsonNotEmpty`, `$jsonDbNull`,
`$jsonNull`, `$jsonAnyNull`, `$jsonNe`), `path: ['metadata']`, an optional
`jsonPath: ['profile', 'country']`, and `value` for value-taking operations.
Existing Filter variables can supply the operand. Top-level objects with
`kind: 'variable'` remain reserved for variable references; pass such literal
JSON through a context variable.

Execution uses SQL on SQLite, PostgreSQL, and MySQL, verified by integration
tests on all three. Oracle and SQL Server currently support only `isDbNull()`;
other JSON predicates fail with `FIELD_CAPABILITY_NOT_SUPPORTED`. There is no
in-memory filtering fallback. Native scalar-list fields remain out of scope.

## Relation aggregates and combine

```ts
await projects.findMany({
  select: (select) =>
    select.fields('id').include('tasks', (tasks) =>
      tasks.filter({ archived: false }).combine({
        records: tasks
          .fields('id', 'title')
          .sort((sort) => [sort.field('id').asc()])
          .limit(10),
        count: tasks.count(),
        total: tasks.sum('points'),
        average: tasks.avg('points'),
        minimum: tasks.min('points'),
        maximum: tasks.max('points'),
      }),
    ),
});
```

Relation builders are immutable: retain or return each chained result. A
combine branch inherits the common scope; additional filters are ANDed with
the common filter. Branch-local sort, limit, cursor, direction and distinct
override the corresponding common setting. Pagination in one branch does not
affect another. `count(field)` excludes NULL values; `count()` counts rows.
Empty scopes yield zero for count and null for the other aggregates. Numeric
aggregate output preserves the driver's number/string/bigint representation.

Aggregates are calculated by SQL over each parent's filtered, distinct and
paginated scope. They support to-many relations only. Paginated aggregates
require direct scalar sort. Relation `distinct(['field'])` requires a direct
sort with a unique tie-breaker; representative selection happens before cursor
pagination. Queries are batched per branch, not per parent. Separate branches
do not imply a shared database snapshot; use an explicit transaction when
snapshot consistency is required.

The include AST retains `select: { kind: 'selection' }` and adds
`result: { kind: 'count' }` or `{ kind: 'sum', field: 'points' }` (also avg/min/max).
For combine, use `result: { kind: 'combine', branches: { count: { select:
{ kind: 'selection' }, result: { kind: 'count' } } } }`. Each branch carries
its own optional filter/sort/limit/cursor/direction/distinct. Record branches
omit result. Aggregate branches cannot select fields or include records.
Selections are bounded to 200 nodes, depth 20, and 32 branches per combine.

Builder aggregate/combine include names and outputs are inferred alongside
root scalar selections. Plain relation-record includes retain the existing
dynamic result fallback; the JSON AST does not provide compile-time inference.

## Remaining contracts

String and text comparisons accept `{ mode: 'insensitive' }` as their second
argument on `eq`, `ne`, `includes`, `notIncludes`, `startsWith`, and `endsWith`.
The Filter AST carries the same `mode` on the condition. Case folding uses SQL
`lower()`; Unicode mappings, accents, and comparison collations remain subject
to database rules. Omitted mode preserves the database default. Pattern values
are literal strings: `%`, `_`, `!`, and `[` are escaped, not user-supplied SQL
wildcards. Equality against null retains SQL NULL semantics.

- Cursor direction defaults to forward; backward returns the preceding page in the original sort order.
- Case-insensitive comparison is explicit and does not change shorthand semantics.
- JSON filters distinguish SQL NULL, JSON null, and missing paths.
- Relation combine branches inherit a common scope and refine independent snapshots. Pagination affects only its own branch; count returns zero for an empty scope and other aggregates return null.
- Junction payloads use the through Collection's logical field names. Relationship keys are managed by Repository. Explicit set payloads update retained junction rows; omitted payloads preserve their existing values.
