# Mail application development

Use the installed Mail plugin's public Client, Server, and HTTP contracts. This Skill guides application integration; changes to the plugin implementation belong in its source workspace under that workspace's development rules.

## Start with the application

1. Inspect the installed `@nocobase/app-plugin-mail` version, public exports and types, `client/plugins.ts`, `server/plugins.ts`, and `config.yml`. Use the installed contracts when versions differ from this guide.
2. Identify the requested surface: account setup, a business mail page, sending from business code, or synchronization and diagnostics. Read the matching reference below; additional references are needed only when the task crosses those boundaries.
3. Implement in the application through public components, service tokens, and APIs. Verify the requested behavior and the relevant ownership boundary using the reference's checks.

| Task                                                                                                                   | Read                                                                             |
| ---------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| Register Mail, configure a provider, connect an account, configure OAuth/push, or replace credential storage           | [Configuration and accounts](references/configuration-and-accounts.md)           |
| Embed a production workspace, connect business records, customize reading/composition, or add management and log pages | [Client integration](references/client-integration.md)                           |

## Ownership and public contracts

The application owns plugin registration, provider configuration, role grants, business-record associations, and production page composition. Mail owns accounts, authorization transactions, credential references, submissions, sync runs, provider cursors, and queue/outbox orchestration. Keep these records behind Mail services; direct table access bypasses lifecycle and ownership rules.

- Register the Client and Server entries in their respective application composition roots. Gmail, Microsoft 365, and IMAP/SMTP definitions are built in; provider instances are configured under `mail.providers`.
- Import Server contracts and `mailServiceToken` from `@nocobase/app-plugin-mail/server`; `server/types` and `server/tokens` are also public subpaths. Resolve services instead of constructing internal stores, operations, or runtimes.
- Import `MailWorkspacePage`, `useMailClient`, and `mailClientToken` from `@nocobase/app-plugin-mail/client`. Public components are also available from `client/components`. Each `ClientApplication` owns its client; use `useMailClient()` in React or `app.services.resolve(mailClientToken)` outside React.
- Plugin-owned `skills/` is the authoritative source. The application's `.agents/skills/` copy is generated by `pnpm plugin:skills:sync`; edit the owning source when a Skill needs correction.

## Access boundaries

| Permission                    | Scope                                                                                                  |
| ----------------------------- | ------------------------------------------------------------------------------------------------------ |
| `page:mail.workspace/access`  | Personal accounts, messages, attachments, sending and sync history; Mail also checks account ownership |
| `page:mail.admin/access`      | Cross-user account overview and settings operation-log API                                             |
| `page:mail.management/access` | All-user message queries, details, attachments and batch actions                                       |

Grant only the requested scope. All-user message management currently has no department or organization restriction. Application-owned routes must authenticate the caller and enforce the appropriate permission; hiding a page or action does not protect its API.

## Integration constraints

- The plugin has development mail pages and a settings account overview, but no standalone production `/mail` page. Production account setup must handle the OAuth return destination as well as render the workspace; see the client reference.
- Submission `accepted` means provider acceptance, not recipient delivery. `unknown` can mean already sent. Before implementing retries or delivery UI, read the sending reference.
- The default credential vault stores plain JSON in the database. Encryption requires an application-supplied vault; see the configuration reference before promising encrypted storage.
- Gate actions by the selected provider's capabilities. IMAP/SMTP has narrower synchronization and mutation support; see the configuration reference rather than assuming Gmail behavior.

## Completion evidence

Run the affected application's checks required by its `AGENTS.md` and scripts, including lint, typecheck, tests and build when application code changes. Select the behavioral checks from the relevant reference; a configuration-only change does not require exercising unrelated features.

Distinguish local/static validation, mocked provider tests, and actual provider results. Registration inspection and Skill synchronization prove composition or file transfer, not successful authorization, delivery, queue processing, or production page availability. Perform live sends and mailbox mutations only within the user's authorized test scope; report external validation that remains unavailable.
