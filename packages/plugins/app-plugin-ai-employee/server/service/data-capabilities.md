# Actor-bound data services

`createDataServices({ database, authorization, actor, timezone? })` returns the seven-method `DataServices` contract from `data-contracts.ts`. Tools reuse `<methodName>Schema` from `data-schemas.ts`; every service method parses its input again. The service captures the actor ID at creation, supplies only a user principal plus the authenticated subject to `AppAuthorization.for()`, and never grants privileges from `isRoot` or role strings.

## Authorization and discovery

Only authorization resources explicitly registered as `<connection>.<collection>` with the `read` action are discoverable. The prefix must exactly match a configured DatabaseManager connection name. There is no default-connection alias, config inspection, connection-string output, or physical-table scan. A missing authorization instance, unmapped resource, unsupported condition, or unresolvable collection fails closed. Discovery hides individual unavailable resources; direct collection operations reject them.

Allowed fields are the intersection of registered fields, the authorization decision's output fields, and supported Collection scalar metadata. Query projections, filters, sorts, groups, aggregate operands, and relation fields must all satisfy this intersection. Native Repository policies carry the same authorization record scope for detail, count, and aggregate/grouped queries. The policy denies all writes and never receives model-provided ASTs or context variables.

## Supported inputs and bounds

- Complete service inputs are limited to 64 KiB of UTF-8 string/key content, 2,000 visited nodes, and eight levels of structure before authorization or database access.
- Catalog and row pages default to 50, with limit 1–100 and offset 0–10,000. Discovery considers at most 1,000 registered resources, 500 fields per collection, and 10,000 matching fields before requiring a narrower search.
- Detail queries require 1–50 explicit scalar fields and accept up to 30 flat AND conditions and 8 scalar sort keys. Use an explicit unique sort for stable pagination. There is no raw SQL, raw AST, arbitrary expression, JSON-path predicate, recursive relation filter, or wildcard field selection.
- Relations are one-hop, same-connection `belongsTo`, `hasOne`, or `hasMany` with explicit foreign and source/target keys. Both join keys must be readable. The source relation and target collection/fields are authorized independently; the target record scope is enforced through the nested Repository policy. At most three includes with 20 fields and 1–10 child rows each are permitted. Child results are capped without a child `hasMore` indicator. Implicit-key, through/many-to-many, cross-connection, nested, and relation-aggregate queries are unsupported and their metadata is hidden.
- Aggregate queries use native `aggregate()` or `groupBy()` only. Up to 20 count/sum/avg/min/max expressions are accepted. Native field capability validation determines legal aggregate operands. Public `Repository.groupBy()` has no SQL limit, so grouped requests must supply explicit value domains: `groupBy: [{ field: 'region', values: ['north', 'south'] }]`. Up to three domains with a Cartesian product of at most 100 values bound the query result before execution. Unknown or unrestricted group discovery, date buckets, HAVING, expressions, and top-N grouping are not supported. Domains narrow the returned data; they are not a claim that other groups do not exist.
- A shared output budget truncates strings to 4,096 characters and at most 100,000 string/key characters across all root and child rows, with `truncated: true` when string values are shortened. Numeric-looking strings are never shortened; an over-budget exact numeric value produces an error. Excessive structure or unsafe numeric output produces an error rather than partial success. Opaque native, blob, and JSON fields are not exposed.

## Numeric and temporal semantics

Big integers become decimal strings, decimal strings remain strings, and unsafe integer numbers or nonfinite numbers are rejected. Native aggregates retain the Repository's result representations. This prevents additional JavaScript conversion loss; it cannot restore precision already lost in physical storage. In particular, SQLite NUMERIC affinity can round nonrepresentable decimals during insertion. SQLite integration tests use an exactly representable large fractional decimal and verify exact native decimal sum output.

The trusted timezone option is validated as an IANA timezone, defaults to `UTC`, and is reported with query results. It does not change native predicate semantics and cannot be supplied by the model. Date fields use exact calendar-date semantics; datetime fields use the Repository's canonical timezone-less timestamp format; datetimeTz fields accept explicit ISO offsets and normalize according to the native temporal contract. There is no inferred user-local day, relative-date language, calendar bucket, implicit DST conversion, or frontend date protocol. `dateOn` applies only to date fields, never timestamp fields; timestamp ranges use explicit `dateNotBefore`/`dateBefore` boundaries. Boolean equality/inequality accepts only true or false, with `empty`/`notEmpty` for nullness.

Membership inputs are nonempty finite OR-of-equality / AND-of-inequality conditions. Trusted authorization `$in`/`$notIn` scopes containing NULL are rejected because translating SQL three-valued membership into null equality would alter the authorized scope. Empty membership and empty authorization disjunctions also fail closed: the Repository omits empty groups, which must never turn a false access predicate into an unrestricted query. Empty conjunctions retain their true semantics, including when nested in a disjunction. Unsupported authorization field types and operators likewise fail closed rather than dropping conditions.

The public Repository read contract has no cancellation or timeout parameter. This service bounds input and result cardinality but does not pretend a Promise timeout cancels the underlying database work; expensive authorized scans remain subject to deployment-level database resource controls.
