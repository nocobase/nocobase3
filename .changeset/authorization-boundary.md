Draw a clear boundary between the `@nocobase/authorization` library and the `@nocobase/app-plugin-authorization` plugin.

The library keeps what a Better Auth style library owns: the core, the Permission Sets, Default Access, Sharing Rules and Restriction Rules plugins with their services, default database stores and Fetch handlers. It no longer ships migrations, the `pages` resource plugin, or the `./pages` and `*/migrations/*` subpath exports. `@nocobase/db` is a type-only import and moves to `devDependencies`; the library has `hono` as its only runtime dependency. The documentation of each plugin now describes the tables its default store expects instead of pointing at a migration.

The plugin owns everything that touches an application: hand-written migrations for those tables, following the pattern `@nocobase/app-plugin-authentication` already uses, the `page` resource plugin, the identity middleware and the administration queries. The four table-creating migrations are written out in full rather than re-exported from the library. Their checksums change as a result: a database that already ran them under 0.2.0-beta.x reports `Executed migration "..." checksum changed` on the next start and needs its `checksum` column for these four rows updated once. The old re-export form hashed one import line, so the real migration body could drift without detection; the inlined form finally covers it.

Protected Permission Sets move into the library. `authz.permissionSets.protect({ owner, keys, allow })` marks code-owned sets, `protection(key)` reports who protects one, and `assertWritable(key, operation)` throws `PermissionSetProtectedError`. The Permission Set handler enforces this on every write and answers `403 PROTECTED_PERMISSION_SET`, so the plugin's duplicated protected routes, its `ProtectedPermissionSetRegistry` and `protectedPermissionSetRegistryToken` are removed. The Hub plugin and the default template register and query protection through `authorization.permissionSets` instead; the owner's own service calls are never blocked, which is what the Hub's role scope relies on.

Transaction binding becomes part of every store contract. `PermissionSetStore`, `DefaultAccessStore`, `SharingRuleStore` and `RestrictionRuleStore` now require `withTransaction(transaction)`, which returns a store bound to the caller's transaction; an in-memory store returns itself. The transaction handle is a generic parameter that the default database stores fix to `DatabaseConnection`, so the services no longer construct the default store themselves. `PermissionSetsApi.withConnection` is renamed `withTransaction` with the same semantics, and the Default Access, Sharing Rules and Restriction Rules APIs gain the same method.

Superuser access becomes unrestricted access: a bypass instead of an enumerated grant list. A Grant Provider may implement `AuthorizationGrantService.unrestricted(identity)`, and a resource handler may implement `authorizeUnrestricted(request)`; the core consults it after it resolves the handler, so an unknown resource type still denies, and permits outright when a handler declares no unrestricted decision. `authz.permissionSets.protect({ owner, keys, unrestricted: true })` declares which Permission Sets confer it and `isUnrestricted(key)` reports it. Declaring it on the protection rather than on its own means a set that confers unrestricted access is always protected as well, which is the only shape that should exist, and the release function `protect` returns lifts both at once. The database handler answers an unrestricted request with an unconstrained `conditional` decision — every record, every field — without consulting Sharing or Restriction Rules, while still rejecting an unknown collection, action or field, because those report a malformed request rather than a permission. The permissions snapshot carries a new required `unrestricted` flag and the client short-circuits `can()` on it. An enumerated administrator set went stale whenever a new resource type or action appeared, and grants alone could never skip a Restriction Rule.

The application plugin now ships exactly two built-in roles. `system-administrator` keeps its key but carries no grants; one `protect` call in code declares it unrestricted, allows `assign` and `revoke`, and requires an active assignment, so an installation can have as many superusers as it needs and cannot revoke its way out of having one. The former `default-pages` set is renamed `authenticated`, titled "All signed-in users", bound to the `authenticated:*` subject and protected with `allow: ['update']`, so its grants stay editable while the set and its binding do not. The plugin's `PUT /permission-sets/system-administrator` route and its administrator grant merging are gone, while the options endpoint still offers `authorization.settings` permissions so an administrator can build their own admin role.

Fixed system records move from migrations to seeds, because migrations create structure. `202608250001_repair_authorization_administrator` and `202608250002_create_default_pages_permission_set` are deleted; the superuser seed now writes an empty grant list, and a new `202608250002_authorization_create_authenticated_role` seed creates the baseline role and its assignment idempotently. Two consequences for an existing installation: its `system-administrator` set keeps the grants it was seeded with, which are now redundant and ignored because unrestricted access short-circuits before grants are read, and its migration history rows for the two removed migrations no longer have a matching source file.

The two Permission Set read endpoints now report what the running application allows for each set. `GET /permission-sets` and `GET /permission-sets/:key` carry `protection` and `unrestricted` alongside the stored set, both derived from the in-code registries and both omitted when they do not apply, so an ordinary set is reported exactly as it is stored. The management panel reads them instead of testing for the `system-administrator` key: a set granting unrestricted access now shows its assignments and an explanation of what holding it means, and offers neither the Permissions tab, the Edit button nor Delete, which removes a Save that the protection answered with `403 PROTECTED_PERMISSION_SET`. Its assignment controls stay enabled because the protection allows `assign` and `revoke`, and adding a second superuser is the only recovery path an installation has; a refused revocation of the last one now reads as an explanation rather than as an error code. Finally, `202609010001_notification_grant_system_administrator` and `202609080001_grant_system_administrator_user_management` are deleted: both appended grants to a set whose unrestricted access short-circuits before grants are read, so nothing could ever read what they wrote. Deleting a seed is safe for an existing database, because the seeder only compares checksums for seeds it still loads.

A route may now declare that being signed in is enough. `access` on an application route widens to `{ resource, action } | false`, and `false` means the page is not authorized at all: every signed-in user reaches it, and no permission change can take it away. The templates honour it in both places a page is authorized — `client/routing/client-page.ts`, which decides whether the page loads, and `client/routing/route-navigation.ts`, which decides whether its navigation entry is shown — so an opted-out page cannot open while its menu entry is filtered away. The Default and Examples templates declare it on their `home` route; the Hub's landing page stays gated behind its `hub` access grant, which is what makes a Hub a Hub. The `authenticated` baseline set is consequently seeded with no grants at all: the landing page used to be a `page:home` grant in it, which an administrator could delete and thereby lock every ordinary user out of the application, and which a route rename silently invalidated.

The pages an administrator may grant access to now come from the client route registry rather than from a hardcoded list on the server. `GET /permission-sets/options` keeps only the `*` page resource, which is meaningful without knowing the inventory, and the Permission Sets page merges in every route that loads a component, requires authentication, declares no `access`, and is not nested under another page — plugin-contributed pages included, which the server could never have listed because page names are declared in client route files. Navigation titles are translated in the owning package's namespace. A stored grant whose page no route declares any more is marked as an unknown page in both the permission summary and the editor, where it can be removed, instead of silently denying access. This makes a route's `name` a stored identifier: renaming one is a data change that has to migrate the grants naming it, which each template's `client/AGENTS.md` now states and a test in each template pins.

The rule that a Permission Set must keep someone able to use it is declared per set rather than derived from unrestricted access. A protection may carry `requireActiveAssignment: true`, which the library enforces in `revoke`, `replaceSubjectAssignments` and the new `assertSubjectRemovable(subject)`; it throws `PermissionSetLastAssignmentError`, which every handler answers as `409 LAST_ASSIGNMENT`. The check takes `PermissionSetStore.lock(key)` before it reads, so two concurrent revocations cannot both see the other assignment each of them is about to remove — the database store locks the set's own row, with a no-op update on SQLite and `SELECT ... FOR UPDATE` elsewhere. It also counts people rather than rows: `permissionSets({ filterActiveSubjects })` lets an application say which subjects can still act, and `@nocobase/app-plugin-authorization` supplies one that drops users whose account is disabled, in one query per check. `system-administrator` declares the flag in the same `protect` call as everything else it owns.

Disabling an account is covered as well as revoking an assignment. `@nocobase/app-plugin-users` asks `assertSubjectRemovable` inside the transaction that disables a user, so the last superuser's account can no longer be taken out of service through a path the revoke rule never saw, and the users API answers `409 LAST_ASSIGNMENT` instead of failing with a 500. An application assembled without authorization disables accounts exactly as before. `@nocobase/app-plugin-hub` replaces its hand-written version of the same invariant — its administrator lock, enabled-administrator count, removal check and `assertCanDisable` role-scope hook — with `requireActiveAssignment` on `hub-administrator`; its API still answers 409, with the code `LAST_ASSIGNMENT` in place of `LAST_HUB_ADMIN`.
