Draw a clear boundary between the `@nocobase/authorization` library and the `@nocobase/app-plugin-authorization` plugin.

The library keeps what a Better Auth style library owns: the core, the Permission Sets, Default Access, Sharing Rules and Restriction Rules plugins with their services, default database stores and Fetch handlers. It no longer ships migrations, the `pages` resource plugin, or the `./pages` and `*/migrations/*` subpath exports. `@nocobase/db` is a type-only import and moves to `devDependencies`; the library has `hono` as its only runtime dependency. The documentation of each plugin now describes the tables its default store expects instead of pointing at a migration.

The plugin owns everything that touches an application: hand-written migrations for those tables, following the pattern `@nocobase/app-plugin-authentication` already uses, the `page` resource plugin, the identity middleware and the administration queries. The four table-creating migrations are written out in full rather than re-exported from the library. Their checksums change as a result: a database that already ran them under 0.2.0-beta.x reports `Executed migration "..." checksum changed` on the next start and needs its `checksum` column for these four rows updated once. The old re-export form hashed one import line, so the real migration body could drift without detection; the inlined form finally covers it.

Protected Permission Sets move into the library. `authz.permissionSets.protect({ owner, keys, allow })` marks code-owned sets, `protection(key)` reports who protects one, and `assertWritable(key, operation)` throws `PermissionSetProtectedError`. The Permission Set handler enforces this on every write and answers `403 PROTECTED_PERMISSION_SET`, so the plugin's duplicated protected routes, its `ProtectedPermissionSetRegistry` and `protectedPermissionSetRegistryToken` are removed. The Hub plugin and the default template register and query protection through `authorization.permissionSets` instead; the owner's own service calls are never blocked, which is what the Hub's role scope relies on.

Transaction binding becomes part of every store contract. `PermissionSetStore`, `DefaultAccessStore`, `SharingRuleStore` and `RestrictionRuleStore` now require `withTransaction(transaction)`, which returns a store bound to the caller's transaction; an in-memory store returns itself. The transaction handle is a generic parameter that the default database stores fix to `DatabaseConnection`, so the services no longer construct the default store themselves. `PermissionSetsApi.withConnection` is renamed `withTransaction` with the same semantics, and the Default Access, Sharing Rules and Restriction Rules APIs gain the same method.

Superuser access becomes unrestricted access: a bypass instead of an enumerated grant list. A Grant Provider may implement `AuthorizationGrantService.unrestricted(identity)`, and a resource handler may implement `authorizeUnrestricted(request)`; the core consults it after it resolves the handler, so an unknown resource type still denies, and permits outright when a handler declares no unrestricted decision. `authz.permissionSets.protect({ owner, keys, unrestricted: true })` declares which Permission Sets confer it and `isUnrestricted(key)` reports it. Declaring it on the protection rather than on its own means a set that confers unrestricted access is always protected as well, which is the only shape that should exist, and the release function `protect` returns lifts both at once. The database handler answers an unrestricted request with an unconstrained `conditional` decision — every record, every field — without consulting Sharing or Restriction Rules, while still rejecting an unknown collection, action or field, because those report a malformed request rather than a permission. The permissions snapshot carries a new required `unrestricted` flag and the client short-circuits `can()` on it. An enumerated administrator set went stale whenever a new resource type or action appeared, and grants alone could never skip a Restriction Rule.

The application plugin now ships exactly two built-in roles. `system-administrator` keeps its key but carries no grants; one `protect` call in code declares it unrestricted, allows `assign` and `revoke`, and requires an active assignment, so an installation can have as many superusers as it needs and cannot revoke its way out of having one. The former `default-pages` set is renamed `authenticated`, titled "All signed-in users", bound to the `authenticated:*` subject and protected with `allow: ['update']`, so its grants stay editable while the set and its binding do not. The plugin's `PUT /permission-sets/system-administrator` route and its administrator grant merging are gone, while the options endpoint still offers `authorization.settings` permissions so an administrator can build their own admin role.

Fixed system records move from migrations to seeds, because migrations create structure. `202608250001_repair_authorization_administrator` and `202608250002_create_default_pages_permission_set` are deleted; the superuser seed now writes an empty grant list, and a new `202608250002_authorization_create_authenticated_role` seed creates the baseline role and its assignment idempotently. Two consequences for an existing installation: its `system-administrator` set keeps the grants it was seeded with, which are now redundant and ignored because unrestricted access short-circuits before grants are read, and its migration history rows for the two removed migrations no longer have a matching source file.

The two Permission Set read endpoints now report what the running application allows for each set. `GET /permission-sets` and `GET /permission-sets/:key` carry `protection` and `unrestricted` alongside the stored set, both derived from the in-code registries and both omitted when they do not apply, so an ordinary set is reported exactly as it is stored. The management panel reads them instead of testing for the `system-administrator` key: a set granting unrestricted access now shows its assignments and an explanation of what holding it means, and offers neither the Permissions tab, the Edit button nor Delete, which removes a Save that the protection answered with `403 PROTECTED_PERMISSION_SET`. Its assignment controls stay enabled because the protection allows `assign` and `revoke`, and adding a second superuser is the only recovery path an installation has; a refused revocation of the last one now reads as an explanation rather than as an error code. Finally, `202609010001_notification_grant_system_administrator` and `202609080001_grant_system_administrator_user_management` are deleted: both appended grants to a set whose unrestricted access short-circuits before grants are read, so nothing could ever read what they wrote. Deleting a seed is safe for an existing database, because the seeder only compares checksums for seeds it still loads.

A route may now declare that being signed in is enough. `access` on an application route widens to `{ resource, action } | false`, and `false` means the page is not authorized at all: every signed-in user reaches it, and no permission change can take it away. The templates honour it in both places a page is authorized — `client/routing/client-page.ts`, which decides whether the page loads, and `client/routing/route-navigation.ts`, which decides whether its navigation entry is shown — so an opted-out page cannot open while its menu entry is filtered away. The Default and Examples templates declare it on their `home` route; the Hub's landing page stays gated behind its `hub` access grant, which is what makes a Hub a Hub. The `authenticated` baseline set is consequently seeded with no grants at all: the landing page used to be a `page:home` grant in it, which an administrator could delete and thereby lock every ordinary user out of the application, and which a route rename silently invalidated.

The pages an administrator may grant access to now come from the client route registry rather than from a hardcoded list on the server. `GET /permission-sets/options` keeps only the `*` page resource, which is meaningful without knowing the inventory, and the Permission Sets page merges in every route that loads a component, requires authentication, declares no `access`, and is not nested under another page — plugin-contributed pages included, which the server could never have listed because page names are declared in client route files. Navigation titles are translated in the owning package's namespace. A stored grant whose page no route declares any more is marked as an unknown page in both the permission summary and the editor, where it can be removed, instead of silently denying access. This makes a route's `name` a stored identifier: renaming one is a data change that has to migrate the grants naming it, which each template's `client/AGENTS.md` now states and a test in each template pins.

The rule that a Permission Set must keep someone able to use it is declared per set rather than derived from unrestricted access. A protection may carry `requireActiveAssignment: true`, which the library enforces in `revoke`, `replaceSubjectAssignments` and the new `assertSubjectRemovable(subject)`; it throws `PermissionSetLastAssignmentError`, which every handler answers as `409 LAST_ASSIGNMENT`. The check takes `PermissionSetStore.lock(key)` before it reads, so two concurrent revocations cannot both see the other assignment each of them is about to remove — the database store locks the set's own row, with a no-op update on SQLite and `SELECT ... FOR UPDATE` elsewhere. It also counts people rather than rows: `permissionSets({ filterActiveSubjects })` lets an application say which subjects can still act, and `@nocobase/app-plugin-authorization` supplies one that drops users whose account is disabled, in one query per check. `system-administrator` declares the flag in the same `protect` call as everything else it owns.

Disabling an account is covered as well as revoking an assignment. `@nocobase/app-plugin-users` asks `assertSubjectRemovable` inside the transaction that disables a user, so the last superuser's account can no longer be taken out of service through a path the revoke rule never saw, and the users API answers `409 LAST_ASSIGNMENT` instead of failing with a 500. An application assembled without authorization disables accounts exactly as before. `@nocobase/app-plugin-hub` replaces its hand-written version of the same invariant — its administrator lock, enabled-administrator count, removal check and `assertCanDisable` role-scope hook — with `requireActiveAssignment` on `hub-administrator`; its API still answers 409, with the code `LAST_ASSIGNMENT` in place of `LAST_HUB_ADMIN`.

An application now says what its own authorization is, under the `authorization` configuration key and in the same shape authentication is configured: which Permission Set confers unrestricted access (`superuser`, with its own `requireActiveAssignment`, or `false` for an application that declares none), and which Permission Set every signed-in user holds (`baseline`, or `false`). `createAppAuthorization` takes the resolved configuration and makes both `protect` declarations itself, so the provider is left resolving configuration and wiring Realtime invalidation, and every default reproduces the previous behaviour exactly. All three templates ship a `server/config/authorization.ts` holding those defaults, and the Default template's role picker reads the superuser key from it — with `resolveAuthorizationSuperuser` exported for that — rather than hardcoding `system-administrator`.

The application also assembles its own Authorization plugin list. `AuthorizationConfig.plugins` is now what the application installs rather than extras appended to a hardcoded set: `defaultAccess`, `sharingRules` and `restrictionRules` are spelled out in each template's `server/config/authorization.ts`, so dropping a capability is deleting a line, and the database `source` field is gone because the plugin reads one connection. The plugin still registers its identity step and installs Permission Sets, database authorization and the `page` resource unconditionally, because each needs something only the plugin has, and the application's plugins are installed after them.

Identity and administration stop being Authorization plugins, because neither is an authorization capability. `Authorization.use(middleware)` is public, so the application registers its identity step directly on the instance instead of wrapping six lines in a plugin shell, and `authz.administration` is gone from the Authorization instance along with the late-binding dance its construction needed. `listUsers` is removed outright — `GET /api/users` already lists users with paging, search and account state — so `GET /permission-sets/users`, `GET /sharing-rules/users` and `GET /restriction-rules/users` no longer exist and the Client's assignment picker reads the Users API. That API authorizes against the `user` resource while these pages authorize against `authorization.settings/*`, so a refusal degrades the page rather than failing it: the assignment list still renders from Authorization's own subject ids, a row nobody can name shows its user id, and adding an assignment is disabled with the reason stated. The record picker is now a plain service constructed where the routes are, and queries through `connection.repository(collection)` rather than a physical table name, which removes the assumption that a collection is its source prefix plus a table.

Which subjects an application has, and which of them can still act, is described by a registry in the core rather than by a callback on Permission Sets. `authz.subjects.define('user', { filterActive })` enriches one subject type: `filterActive` is handed the ids of that type alone, batched so one query answers the whole set, plus the transaction the caller is holding. Declaring a type is optional and never validation — subject types stay open strings, adding a subject consults nothing, and an undeclared type passes through, which is why an audience such as `authenticated:*` is always active. The last-assignment guard asks the registry instead of `permissionSets({ filterActiveSubjects })`, which is removed. `@nocobase/app-plugin-users` declares the `user` type in its provider's `boot`, querying its own user administration API, so `@nocobase/app-plugin-authorization` no longer reads the `user` table at all.

`permissionSets({ rootSet })` gives the library the concept an application used to assemble by hand: `rootSet: 'system-administrator'`, or `{ key, requireActiveAssignment: false }`, declares a protection owned by the library itself with `allow: ['assign', 'revoke']`, `unrestricted: true` and `requireActiveAssignment` defaulting to true, so the flag that keeps the last superuser in place can no longer be forgotten. `onAssignmentsChanged` becomes a subscription taken after construction — `authz.permissionSets.onAssignmentsChanged(listener)` returns a release function, and a service bound to a transaction notifies nobody, the caller publishing after it commits. Consequently `AuthorizationConfig` loses `superuser` and `source` and keeps `baseline` and `plugins`, and each application assembles the whole list, `permissionSets({ rootSet })` and `pages()` included. Deleting the `permissionSets` line is the one line whose removal stops an application from booting, because nothing else provides grants.

Each Authorization plugin now serves its own HTTP surface and registers it with the instance. `authz.routes.add(path, handler)` is a registry in the core alongside `resources`, `constraints` and `subjects`: a plugin claims a path during `setup`, a second plugin claiming the same one throws, and `routes.handle(request)` dispatches by path. Permission Sets, Default Access, Sharing Rules and Restriction Rules each register their own list, create, update and delete routes, parse their own request bodies and check their own `authorization.settings/<id>` permission — `PUT /default-access` still choosing `create` or `update` depending on whether the rule exists. Paths, payloads, status codes and error codes are unchanged.

The application's route file mounts its own endpoints — `GET /permissions`, the permission option endpoints and the record pickers — and then one dispatcher, so a plugin an application did not install has no route rather than a guarded one, and nothing in the application names a plugin any more. `AppAuthorization` is consequently `Authorization & PermissionSetsAuthorizationApi`: everything else a plugin contributes is reached through `authorize()` or through the route registry, so a type can no longer promise a member the plugin list does not provide. `createAppAuthorization` verifies the Permission Sets plugin it protects the baseline through and throws naming it, instead of asserting the whole shape.

Both code-owned Permission Sets are now declared on the Permission Sets plugin, and both are renamed. `permissionSets({ rootSet, defaultSet })` protects the superuser set as before and adds the ordinary one — protected, grants editable, set not deletable, its binding not revocable — so the application no longer writes that `protect()` call itself and `AuthorizationConfig.baseline` is gone. `defaultSet` names a set and its protection; it does not mean "these grants apply to every identity without an assignment", which still comes from the `authenticated:*` assignment row and the host's identity step, because the library's "every identity" would include anonymous ones in a host that has them. The keys become `root` and `member`, the names NocoBase v2 uses, which also ends the collision between the `authenticated` set key and the `authenticated` subject type. A database seeded by an earlier beta keeps its rows under `system-administrator` and `authenticated`: the renamed seeds create the new sets alongside them, and the old rows are left orphaned rather than migrated.

Announcing that grants changed belongs to the Grant Provider rather than to one plugin. `AuthorizationGrantService.onChange` is optional on the contract, `Authorization.onGrantsChanged(listener)` subscribes through whichever provider is installed and returns a release function, and Permission Sets implements it with the subscriber list it already had — a service produced by `withTransaction` still notifies nobody. `permissionSets.onAssignmentsChanged` is replaced by that one member, so a host wires cache and Realtime invalidation without naming a plugin. With that and the two sets moved, `createAppAuthorization` no longer touches `permissionSets`, so `AppAuthorization` is removed and the application's Authorization is just `Authorization`; a consumer that requires an api states it itself, narrowing with the exported `hasPermissionSets(authz)`. Finally, `basePath` is gone: the dispatcher derives its mount from the route pattern it matched, so a router mounted under an extra prefix serves the plugin surfaces instead of answering 404 on all of them. Every URL is unchanged.

Finally, the plugin ships no default Authorization plugin list at all. `createAppAuthorization` installs exactly what `AuthorizationConfig.plugins` names and nothing when an application names none, so the application's own `server/config/authorization.ts` is the only source of that list.

At the application layer, Permission Sets is not optional. `@nocobase/app-plugin-authorization` installs it itself, ahead of whatever `AuthorizationConfig.plugins` names, and an application configures it through `permissionSets: { rootSet, defaultSet }` — defaulting to `root` and `member` — rather than assembling the plugin into its list. `createAppAuthorization` therefore returns `Authorization & PermissionSetsAuthorizationApi` honestly, and the `hasPermissionSets` guard with its `Reflect.get` probe is deleted. The api is exposed as its own service, `permissionSetsToken`, which the Hub, the users plugin and the templates' role pickers resolve instead of probing the Authorization instance; a consumer that works without it asks `container.has(permissionSetsToken)`.

A protection may now restrict which subject types a Permission Set can be assigned to. `assignableTo` on `protect()` — and on `permissionSets({ rootSet: { key, assignableTo } })`, which passes it through — makes `assign()` and `replaceSubjectAssignments()` refuse a subject of any other type, answered as `403 PERMISSION_SET_SUBJECT_NOT_ALLOWED` by the handler; existing assignments are not rechecked. The library declares no default, because which types are accounts rather than audiences is the host's convention: `@nocobase/app-plugin-authorization` declares `assignableTo: ['user']` for its root set, so `POST /api/authz/permission-sets/root/assignments` with `authenticated:*` — which used to make every signed-in user unrestricted — is refused. The Client reads the same metadata: the assignment picker offers only the subject types the server allows, so the audience option is gone for the root set while assignments that already exist still display.

The database resource plugin moves out of the library and into the application plugin, as `@nocobase/app-plugin-authorization/server`. It was always an adapter between authorization's grant model and a storage model, and it now speaks `@nocobase/db`'s types natively: Record Access policies return literal filter nodes instead of the plugin's own `DatabaseFilter` mini-AST, positive scopes are `or`-ed and restrictions `and`-ed into one `FilterAst`, and a decision carries `{ scope, fields }` rather than a filter object a caller has to compile. `@nocobase/authorization` no longer has a `./database` entry; what remains there — the core, Permission Sets and the three rule plugins — produces opaque scope references for a resource plugin to interpret, which is what it always did.

That plugin also takes no options any more. The resource id of a collection is its name — `orders`, not `main.orders` — because the plugin reads one connection and a prefix only ever named that one, while the permission options endpoint had always offered the bare name, so a grant an administrator created through the UI could not match a lookup the authorizer prefixed. Grants written as `main.<name>` on this unreleased branch are not migrated.

`authz.db.policyFor(collection, scope)` folds a request's read, create, update and delete decisions into one `RepositoryPolicy`: a deny is `false`, a permit is `true`, and a conditional decision is `{ scope, fields }`. `repository.withPolicy(policy)` binds it, so a route runs plain `findMany`, `createOne` and `updateOne` and the Repository applies the row scope and the field allowlist. The Examples template's articles module drops its hand-written filter compiler and field filtering accordingly. A write grant must now name every column the caller stores, timestamps included, because a generated primary key is not writable and `fields: { input: '*' }` expands to every registered field.

The four default database stores move to the application plugin as well, beside the migrations that create their tables, so a store and its schema ship together. Each library plugin now requires a `store`, the fallback that built one from a connection is gone, and the library no longer references `@nocobase/db` at all — `hono` is its only dependency of any kind. The connection becomes an opaque handle: `createAuthorization({ connection })` types it as the caller chooses and threads it, uninspected, to every plugin's `setup`, which is how `@nocobase/app-plugin-authorization`'s `defaultAccess`, `sharingRules` and `restrictionRules` hand a database store its connection. Transaction handles default to `unknown` rather than to `DatabaseConnection`, so an application that types one states it, as `subjects.define<DatabaseConnection>('user', …)` now does.

Database authorization is a built-in plugin rather than one an application lists, and it is reached as `authz.db`. `createAppAuthorization` installs it as a fixed element of the plugin tuple beside Permission Sets, so `authz.db` is statically typed and the `appAuthorizationDatabase(authz)` accessor with its `Reflect.get` probe is deleted along with every "database plugin not installed" branch: a connection can still be missing, and the plugin already denies that with `DATABASE_UNAVAILABLE`. The three templates drop `databaseAuthorization()` from their `plugins` arrays, and the constructor is no longer exported.

The metadata registry that was removed earlier does not come back; a registry of intent takes its place. `authz.db.collections.add('orders')`, or `add({ name, title, description })`, records that a Collection is part of the permission model and nothing else — field names, the primary key and whether the database generates it keep coming from db at authorize time, so the two can never disagree. `has` and `list` complete it, and `add` never touches db, because registration happens at boot before a connection is necessarily usable; repeating an identical registration is a no-op, since boot runs more than once in some hosts, while one that disagrees with what is already registered throws. Registration is always explicit, and that is what lets a Collection carry the label the permission UI shows: `authz.db.repositories()` registers nothing, so an exposure naming an unregistered Collection is refused like any other request for it rather than quietly registering a Collection with no name to show.

**A Collection nobody registered has no permission.** Both `authorize` and `authorizeUnrestricted` deny with `COLLECTION_NOT_REGISTERED` before any metadata or grant lookup, an unrestricted identity included — a superuser bypasses grants, not the model — so `policyFor` returns all-false and a Repository endpoint answers 403 through the existing `READ_FORBIDDEN` and `WRITE_FORBIDDEN` mapping. This is the point of the change: listing every Collection db reports was wrong, because it offered session, migration and permission-set tables as things an administrator could grant on, and `listCollectionNames` is deleted with it — which also removes the crash on a database holding tables db cannot map to a logical name. The permission options endpoint now lists the registered Collections alone, showing each registration's `title` and `description` and reading `fields` from db for the field pickers, and the settings record picker answers "not found" for anything unregistered, so records cannot be picked from outside the model.

A resource is still the collection name alone; the actions are the fixed `read`, `create`, `update` and `delete`, since db exposes no action of its own. `fields: { input: '*' }` is safe for a create, because it expands to the collection's columns minus a primary key the database assigns. Grants keep their stored shape, so no data migrates. The `attributes.owner` and `attributes.creator` mappings are replaced by a parameter on the rule that used them, `recordsIOwn` and `recordsICreated` taking `params.field` and defaulting to `ownerId` and `createdById`. A field the collection does not have denies with a reason rather than throwing.

`authz.db.repositories(exposures)` authorizes `defineRepositoryApiRoutes()` endpoints and computes policies only; the Collection an exposure names is registered by the provider that owns it, at boot. It returns a Hono middleware that also carries `principal` and `repositories` to hand straight to the definer: mounted on an endpoint, it resolves the caller's identity, folds their grants for that exposure's `resource` into a Repository Policy, and narrows the exposure's declared shape with it. The direction matters — a grant carries no relation model, and `narrowRepositoryPolicy` leaves a member the patch does not mention as it was, so relation rules come from the shape while scope and fields are intersected with the grant; a shape whose `read` is `true` narrows to a node with no readable relations, so an exposure that reads relations writes `read` out as a node. An exposure that names a `resource` must declare a static `policy`, and a function throws a `TypeError` where the routes are defined. An action the middleware was not mounted on resolves no principal, and app-server answers `403 PRINCIPAL_REQUIRED` rather than falling back to the shape — the `principal` resolver's type now admits the `undefined` that path has always returned. An exposure with no `resource` is passed through untouched. `@nocobase/app-plugin-authorization-example` is the worked reference. A service provider of its own registers the collection at boot, with the title and description the permission UI shows, so the route files build routes and nothing else, and it shows both scenes over one owned collection: the generated Repository API endpoints, each guarded by name so a wildcard cannot reach a contribution mounted beside them, and a hand-written create route that stamps `ownerId` from the principal because the definer would take it from the request body. Its seed grants every signed-in user `recordsIOwn` on that collection, so an ordinary account sees only its own rows while a holder of the root set sees them all. The Examples application also installs `@nocobase/app-plugin-users`, which the Permission Sets panel reads to name the people an assignment can be given to: the panel authorizes against `authorization.settings` while accounts come from the Users API, so an application without that plugin lists assignments by raw user id and cannot add one.

The settings module now renders on the same vendored shadcn components and theme tokens as the rest of the application, with one page shell and shared loading, error and forbidden states, and the permission sets panel split into focused files; no route, endpoint or behaviour changed.

The settings screens carry that treatment further. Every toolbar holding a filter is a defined bar rather than loose controls on the page background, its search field clears itself, and a bar with more than one filter offers to return them all to their defaults. The permissions tab lists one row per resource with the actions as columns, each collection cell showing whether that action starts from every record, from a scoped set, or is not granted at all, with a legend naming the three. Long lists — the permission sets, the assignments, the three rule lists and that tab — page ten rows at a time over rows the panel already holds. No behaviour, route or endpoint changed.

The four authorization plugins are separable packages, so the settings module keeps each of them to its own screen: the permission sets page is a list, a detail and the editor, and nothing reads across Default Access, Sharing Rules and Restriction Rules. The three cross-plugin views that briefly existed on this branch — Resource access, Compare two sets and User access — are gone with the one endpoint they needed, `GET /api/authz/permission-sets/assignments`, which nothing else called.

Every destructive action in the module now confirms before it runs: deleting a permission set, a default access rule, a sharing rule or a restriction rule, removing a granted resource from a set, and revoking an assignment. One `ConfirmDialog` over a vendored `dialog.tsx` serves all of them, naming what is about to happen and to what, opening its focus on cancel, and leaving on Escape or a backdrop click. Confirmation runs before the call, so every existing failure path is unchanged.

The permissions tab now opens on every resource the set grants in one table, laid out so the rows do not compete for width: the resource on one line, truncated with the full value in its `title`, and its type quietly beneath it rather than in a column of its own; each granted action carrying the mark that says what it reaches and its name beside it, a label never splitting across lines while the column wraps between them; and, for a collection, its records and its fields as two short clauses, such as `Records I own, selected fields`, saying `Mixed records` once where the actions disagree rather than listing every one. That clause now reads the record access policy's label from the options endpoint, where it previously rendered the stored key as `RecordsIOwn`; the same fix reaches the editor's resource summary and its per-action summary, which had the same bug. The filter bar drops its Edit permissions button, which duplicated the Edit already in the detail header. Opening a resource reports each of its actions: whether it is allowed, the record access policy and the parameters stored with it, and the writable and visible fields by name. The permission set list drops its permissions count, which counted entries in a stored structure that an administrator cannot act on.

The settings module is translated. It shipped with its strings hardcoded in English; `client/locales/` now carries `en-US` and `zh-CN` catalogues loaded one dynamic import at a time and registered as the client plugin's `locales`, and every screen translates under the package name as its namespace, the way the Hub does. Keys are structured by screen rather than flattened into sentences, and the label helpers that compose a summary take the translator as an argument instead of holding English.

The vocabulary the options endpoints send is translated too, on the server. Resource type names, resource and action labels, subject types and the built-in record access policy titles were English literals in the route file; they now resolve against the request's locale from a `server/locales/` catalogue registered as the server plugin's `locales`, under the same namespace as the client's. The wire format is unchanged — every option still carries `label` and an optional `description` as plain strings — so no client threads a translator to render them and nothing outside the plugin has to change. Each call passes today's English as its default, so a host that mounts no i18n middleware sends exactly what it sent before.

A `title` or `description` registered with `db.collections.add()` or `defineRecordAccessPolicy()` may now be `{ key, ns }` instead of a string, resolved the same way and falling back to its last segment humanised when nothing declares it. A string is still used as written, which is what every existing caller passes. The key form is what lets a server-only plugin name its Collections in the reader's language, which a client-side translation could not have done: the browser has no catalogue for a package that ships no client bundle.

The permissions table now has one shape whatever is in it. It branched on the collection resource type in eight places and swapped its columns between the combined view and a per-type view, which a type chip selected; resource types are registered at runtime, so a settings table that names one of them cannot render the next. The chips now filter rows and nothing else, and what a type adds — its summary cell, whether a granted action reaches the whole resource or a scoped part of it, and what the side panel reports under each action — comes from a presentation that type registers. The database module registers the one for Collections; a type that registers nothing renders correctly, with each action reaching the whole resource and an empty summary cell. The per-type tables, where the actions became columns, are gone.
