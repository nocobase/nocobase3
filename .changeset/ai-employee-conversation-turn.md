Separate a conversation turn, its transport, and one agent call

One `aiConversations:sendMessages` request used to be unpacked four times. The route parsed the body into a `ConversationExecution`, `AIConversationService` parsed the same body again, assembled an `execution` plus a hand-written `state` plus flat `webSearch`/`frontendTools`/`sessionId` options, and `AgentServiceFactory.resolveState()` merged all three with a fallback chain. `sessionId`, `messages`, `messageId`, `model`, `webSearch`, `frontendTools` and `important` each had four homes, and the model was resolved twice — once into the agent state and once onto every `AgentRequest`.

`ConversationExecution` is replaced by two types that do not overlap. `ConversationTurn` is what a turn asks for and is parsed in exactly one place, `parseTurn()` in the route; `ConversationTransport` carries the SSE target, the abort signal, `translate` and `getHeader`, and stops at the conversation service, so an agent can no longer be handed a stream target. `CreateEmployeeOptions` and `CreateAgentOptions` take that turn whole and drop `execution`, `state`, `webSearch` and `frontendTools`; the conversation-level `systemPrompt`, `skillSettings` and `tools` stay flat on the options and are read by one `conversationAgentOptions()` helper rather than by four copies of the same three type guards.

A turn no longer carries a session. The conversation an agent runs in is decided by whoever creates it — a sub-agent runs in its own — so `sessionId` is named once, on `CreateEmployeeOptions`, and `toAgentState()` takes it as a decided value rather than falling back to the turn. `AIConversationService` takes it as its own parameter alongside the few other fields each action reads (`aiEmployee`, `stream`, `messageId`, `toolCallId`, `userDecision`), so no action receives the whole request body any more; the route validates it with `requiredString` as it already did for `abort`. `aiConversations:updateUserDecision` therefore reports `sessionId is required` rather than `Invalid request` for a missing session id, with the same 400 status.

The model is now resolved once, by `AgentServiceFactory`, against the employee's own policy. `AgentRequest` therefore loses `model` and `context`: `AgentContextProvider.resolveLLM()` takes no argument and reads the agent's own state, which the new `AgentContextProvider.state()` exposes, and the `important` retry prompt reads that state too. What is left on a request is what genuinely varies per call — `userMessages`, `userDecisions`, `messageId`, `writer`, `signal` — plus `runtime`, the renamed middleware channel that carries `appendMessages`.

Two defects fell out of the reshuffle. `from` was computed as `execution.sessionId === sessionId ? 'main-agent' : 'sub-agent'`, but the route derived both from `input.sessionId`, so the branch never chose `sub-agent`; the main conversation path now states `main-agent` outright and `SubAgentsDispatcher` keeps passing `sub-agent`. Two `if (shouldStream) {}` blocks that did nothing are gone.

An `AgentContextProvider` implemented outside this package has to add `state()` and change `resolveLLM(request)` to `resolveLLM()`. A caller that passed `execution`, `state`, `webSearch` or `frontendTools` to `createAIEmployee()`/`createAgent()`, or `model`/`context` on an `AgentRequest`, passes a `turn` instead, and a caller that put `sessionId` in either of those passes `sessionId` on the options. The HTTP contract is unchanged.
