# I18n

这份文档定义 NocoBase V3 的国际化方案：app（`app-template-default` 生成的用户项目）和插件（`@nocobase/app-plugin-*`）如何各自声明翻译资源，如何统一切换语言，以及前后端分别怎么用。

方案的目标是：能力全部封装在 SDK 里，模板升级时用户项目里需要改动的代码尽可能少。用户项目里应该只剩下"我自己的翻译文案"和"语言切换器摆在哪"，其余机制都在 `@nocobase/app-sdk` 内部演进。

## 现状

现有实现散落在三个地方，都属于上一代 portal 体系，新架构下需要重做：

- `@nocobase/app-portal-sdk/i18n` 有一套可用的核心（i18next 实例、locale 注册表、`registerTranslationResources`、Refine `i18nProvider`、`{{t('...')}}` 表达式解析）。能力不弱，但它是 portal 的包，而 portal-sdk 长期要下掉。
- `packages/app-template-default/registry/nocobase-i18n/` 里的 `provider.tsx` 和 `server-resources.ts` 承担了 bootstrap、服务端资源拉取、namespace 懒加载。这些是运行时机制，却会随 Registry materialize 进用户项目——一升级就要改用户代码，正是要解决的问题。
- `packages/app-template-default/client/`（当前架构）里完全没有 i18n，只有 `client/refine-runtime.ts` 预留了 `setI18nProvider` 的槽位。服务端则完全没有 i18n：前端调用的 `app:getLang` 和 `users:updateLang` 在 `app-server-kit` 里并没有对应实现。

插件包目前一个 `locales/` 目录都没有，`defineClientPlugin` 和 `defineServerPlugin` 也没有 i18n 贡献入口。所以这不是改进，是在新架构上重建一次。

## 包的归属

不新建 `@nocobase/app-i18n`，全部放进 `@nocobase/app-sdk`。portal-sdk 长期要下掉，其能力都会收敛到 app-sdk，i18n 没有理由单独再开一个包。

`app-sdk` 当前只有 `src/client.ts` 和 `src/index.ts` 两个文件，一个根导出，tsconfig 用的是 `client-library.json`。要承载 server 代码需要调整为多入口，且 Node 与浏览器代码分开：

```
@nocobase/app-sdk
├── .            现有的 AppClient / resolveAppUrl，保持不变
├── ./i18n       core：同构，无 React、无 hono，依赖 i18next
├── ./i18n/client  React 绑定、Refine 适配、LanguageSwitcher
└── ./i18n/server  hono 中间件、请求级 translator、i18n API 路由
```

`./i18n/server` 引入 Node 与 hono，因此 tsconfig 需要从 `client-library.json` 改为 `server-library.json` 并在本地补 DOM lib（与 `app-host` 的做法一致，见根 `AGENTS.md`）。`hono` 作为 `optionalDependencies` 不合适，它应当是 `peerDependencies` 且只被 `./i18n/server` 引用——浏览器构建不会走到那个入口，所以不会被打进前端产物。`i18next` 与 `react-i18next` 是 `dependencies`，`react` 保持 peer。

依赖方向：

```
                @nocobase/app-sdk/i18n  (core)
                    ↑              ↑
   @nocobase/app-sdk/i18n/client   @nocobase/app-sdk/i18n/server
              ↑                              ↑
     @nocobase/app-client            @nocobase/app-server-kit
              ↑                              ↑
        app-template-default  /  @nocobase/app-plugin-*
```

`app-client` 和 `app-server-kit` 依赖 app-sdk 并在各自 runtime 里自动接线，app 和插件作者则直接从 `@nocobase/app-sdk/i18n/client` 和 `@nocobase/app-sdk/i18n/server` import。

`app-portal-sdk/i18n` 在过渡期保留，内部改成对 app-sdk core 的薄转发，导出签名不变。关键在于两边必须共用同一个 i18next 实例，否则会出现两套资源、两次 `changeLanguage`、语言切换不同步。`parseTranslationExpression`（解析 `{{t('key', { ns: 'x' })}}`）这块逻辑很有价值，整体搬进 core。

## Namespace

### 用包名作为 namespace

namespace 直接取 `packageName`，不给插件额外的 `namespace` 配置项。包名本身在 npm 上就是唯一的，天然不会冲突，也就不需要冲突检测和显式声明的逃生舱。

| 来源           | ns                                                                                        |
| -------------- | ----------------------------------------------------------------------------------------- |
| app            | `package.json` 的 `name`，模板默认 `@nocobase/app-template-default`，用户项目是自己的包名 |
| 官方插件       | `@nocobase/app-plugin-workflow`                                                           |
| 第三方插件     | `@acme/app-plugin-crm`                                                                    |
| SDK 内置通用词 | `@nocobase/app-sdk`                                                                       |

代价是显式写 ns 时字符串很长。这个代价通过两条路化解：一是绝大多数情况根本不需要写 ns（下面的默认 ns 机制），二是需要写的时候引用常量而不是字面量。每个包从自己的 locales 模块导出 ns 常量：

```ts
// packages/app-plugin-workflow/client/locales/index.ts
export const WORKFLOW_NS = '@nocobase/app-plugin-workflow';
```

app 的 ns 常量由 SDK 提供 `APP_NS`，插件想复用 app 的翻译时写 `t('save', { ns: APP_NS })`，不用关心 app 实际叫什么包名——这一点很重要，因为用户项目的包名是用户自己起的，插件不可能知道。

### fallback 链

i18next 的 `fallbackNS` 让"复用 app 翻译"变成零成本。每个 ns 的解析顺序是：

```
当前 ns  →  app ns  →  @nocobase/app-sdk
```

于是插件里 `t('save')` 会先找自己的 `save`，没有就落到 app 的，再没有就落到 SDK 内置的通用词（保存、取消、确认、分页这类）。**插件不写任何 ns 就已经能复用 app 的词条**，需要显式指定时 `t('label', { ns: APP_NS })` 依然可用。这比要求插件到处标注 ns 好得多。

反过来，app 覆盖插件文案也要支持，模板用户一定会提这个需求——插件的某句话不合业务口径，但不想改插件源码。app 的 locale 文件里给一个 `overrides` 段：

```ts
// client/locales/zh-CN.ts
export default {
  welcome: '欢迎',
  overrides: {
    '@nocobase/app-plugin-workflow': {
      'trigger.title': '触发条件',
    },
  },
};
```

实现就是在所有插件资源注册完成之后，对每个被覆盖的 ns 调一次 `i18n.addResourceBundle(locale, ns, {...}, true, true)`。顺序由 SDK 保证，用户不需要关心。

### 默认 ns 怎么做到"不用输入"

两条路并存，覆盖不同场景。

**模块级绑定（推荐主路径）**

工具函数、`defineClientPlugin` 的静态元数据、zod 校验消息里都没有 React context，所以需要一个不依赖 context 的绑定方式：

```ts
// packages/app-plugin-workflow/client/locales/index.ts
import { defineNamespace } from '@nocobase/app-sdk/i18n/client';

export const {
  ns: WORKFLOW_NS,
  t,
  useT,
  Trans,
} = defineNamespace('@nocobase/app-plugin-workflow', {
  'en-US': () => import('./en-US.js'),
  'zh-CN': () => import('./zh-CN.js'),
});
```

插件内部统一 `import { useT } from '../locales'`，然后 `const t = useT(); t('trigger.title')`。这条路 tree-shaking 友好、类型可推导、在组件内外都能用。**插件模板默认走这条。**

`defineNamespace` 一次做完三件事：注册 ns、登记该 ns 的 locale loader、返回绑定到这个 ns 的 `t` / `useT` / `Trans`。它是幂等的，同一个 ns 重复调用返回同一组绑定。

**React context 自动注入（便利路径）**

`app-client` 的每个贡献都记录了 `packageName`（`AppClientRegisteredRoute`、`AppClientRegisteredProvider`、`AppClientRegisteredSetting` 上都有这个字段）。所以在路由、provider、settings 的渲染层由 SDK 自动包一层：

```tsx
<NamespaceScope ns={route.packageName}>
  <Page />
</NamespaceScope>
```

插件页面里直接 `useTranslation()` 拿到的就是自己 ns 的 `t`，不需要任何声明。

这条路有个必须写进文档的陷阱：**插件导出给 app 复用的组件，渲染时 context 是 app 的 ns，不是插件的。** 因为 context 跟着渲染树走，不跟着代码所有权走。这类跨 ns 边界的组件必须显式绑定，用模块级绑定的 `useT`，或者 `withNamespace(NS)` 包一次。这也是为什么模块级绑定是推荐主路径而 context 只是便利。

## 翻译资源

### 文件格式

用 TS 模块，不用 JSON。用户拿到的是源码级项目，TS 有类型、能推导、能写注释，也能被 `defineNamespace` 的 loader 直接动态 import。JSON 的优势在对接翻译平台，那是后面的事——真要接的时候可以加一个导出脚本把 TS 转成 JSON 给平台，再把回稿转回来，不需要现在就为它牺牲开发体验。

按语言分文件，`en-US` 是 source of truth：

```
client/locales/
├── index.ts      defineNamespace(...)
├── en-US.ts      默认导出扁平或嵌套对象
└── zh-CN.ts      satisfies Partial<typeof enUS>
```

`zh-CN.ts` 用 `satisfies` 约束到 `en-US` 的结构，写错 key 立刻报错，但缺 key 不报错（允许未翻译的部分回落）。缺失的 key 由 `pnpm i18n:check` 脚本报告，不阻断开发。

`keySeparator` 开启 `'.'`（嵌套结构可读，locale 文件能分组），`nsSeparator` 关闭（避免 key 里的冒号被误解析成 ns）。ns 一律走 options 传递。注意这和 portal-sdk 当前 `keySeparator: false` 的配置不同，是有意的改变，转发层要处理这个差异。

### 三类资源

| 类别           | 来源                                                            | 加载时机                                         |
| -------------- | --------------------------------------------------------------- | ------------------------------------------------ |
| 前端静态文案   | 包内 `client/locales/<locale>.ts`                               | 按当前语言懒加载；切换语言时按需加载新语言       |
| 服务端静态文案 | 包内 `server/locales/<locale>.ts`                               | 进程内直接持有，无懒加载                         |
| 服务端动态文案 | 数据库：用户自建 collection 的显示名、workflow 节点标题、角色名 | 前端按 ns 向 i18n API 拉取；服务端翻译时按需查询 |

第三类是现在 `server-resources.ts` 里 `lm-collections` 那套的正规化版本。

### 前端初始化时机

现在的 `NocoBaseI18nBootstrap` 用一个全屏 Loading 遮住整个应用等资源加载，体验差。新方案把 i18n 初始化提到 `createAppRuntime()` 里——它本来就是 async，且在 `root.render` 之前执行：

1. 解析初始 locale：`localStorage` → 用户 profile（已登录时来自 i18n bootstrap 响应）→ `navigator.language` → app 配置的默认值
2. 收集所有 contribution 声明的 ns（app 的 + 每个插件的）
3. 并行加载这些 ns 的当前 locale 静态资源
4. `i18n.init()`
5. 才 `root.render`

代价是首屏多一批并行的动态 import，都是本地 chunk，很快。换来的是零闪烁、零 Loading 遮罩，且第一帧就是正确语言。服务端动态资源不阻塞首屏，异步合并进来后触发重渲染。

### 语言列表与用户偏好

统一由一个接口返回，替掉现在 `getLang` 加 system-settings 两处分散的逻辑：

```
GET /api/i18n/bootstrap?ns=<ns>,<ns>
```

```jsonc
{
  "locale": "zh-CN", // 服务端为当前用户/请求决议出的语言
  "defaultLocale": "en-US",
  "enabledLocales": [
    { "locale": "en-US", "label": "English" },
    { "locale": "zh-CN", "label": "简体中文" },
  ],
  "resources": {
    // 只含请求的动态 ns
    "@nocobase/app-plugin-workflow": { "node.custom.42": "审批节点" },
  },
}
```

一次请求解决语言列表、当前语言、动态资源三件事。

用户偏好持久化：

```
PUT /api/i18n/preference   { "locale": "zh-CN" }
```

未登录时只写 `localStorage`，登录后写 profile 并同步 `localStorage`。

`enabledLocales` 由 app 配置决定（`server/config/i18n.ts`），不再挂在 System Settings 上。

## 前端接入面

### 插件

`defineClientPlugin` 增加 `locales` 入口，和现有四个 loader 平级：

```ts
// packages/app-plugin-workflow/client/plugin.ts
export default defineClientPlugin({
  packageName: '@nocobase/app-plugin-workflow',
  locales: () => import('./locales/index.js'),
  bootstrap: () => import('./bootstrap.js'),
  routes: () => import('./routes.js'),
});
```

`locales` 模块默认导出 locale 到 loader 的映射，和 `defineNamespace` 的第二个参数是同一个对象，写一次复用：

```ts
// client/locales/index.ts
import { defineNamespace } from '@nocobase/app-sdk/i18n/client';

const resources = {
  'en-US': () => import('./en-US.js'),
  'zh-CN': () => import('./zh-CN.js'),
};

export const { ns, t, useT, Trans } = defineNamespace(
  '@nocobase/app-plugin-workflow',
  resources,
);

export default resources;
```

`createAppRuntime` 收集所有 `locales` 声明，用 `packageName` 作为 ns 注册，按当前 locale 并行加载。**插件作者要做的只有两件事：加一个 `locales` 字段，写 locale 文件。** ns 分配、加载、语言切换响应、fallback 全在 SDK 里。

### app

同样的写法，走 `defineClientApplication`：

```ts
// client/application.ts
const application = defineClientApplication({
  packageName: '@nocobase/app-template-default',
  locales: () => import('./locales/index.js'),
  bootstrap: () => import('./bootstrap.js'),
  providers: () => import('./providers.js'),
  routes: () => import('./routes.js'),
});
```

SDK 认出 `source: 'application'` 的那个贡献，把它的 ns 记为 app ns，也就是 `APP_NS` 和 fallback 链第二级指向的东西。

### 语言切换

SDK 出品，模板只负责摆位置：

```tsx
import { useLocale, LanguageSwitcher } from '@nocobase/app-sdk/i18n/client';

const { locale, locales, setLocale, switching } = useLocale();
```

`setLocale(next)` 的完整流程封装在 SDK 内：

1. 并行加载所有已注册 ns 的 `next` 语言资源
2. `i18n.changeLanguage(next)`，i18next 广播 `languageChanged`
3. 更新 `<html lang>` 和 `<html dir>`
4. 持久化：`localStorage`，已登录时同时 `PUT /api/i18n/preference`

第 1 步是"所有 ns 一起等"，所以切换是原子的，不会出现半中半英的中间态。

插件自动响应语言切换（这是需求里的第 2 点）不需要任何插件侧代码：所有 ns 共用同一个 i18next 实例，`useTranslation` 底层订阅 `languageChanged`，插件组件自然重渲染。这是"一个全局实例 + ns 分区"相对于"每插件一个实例"的直接收益。

模板里的接线只有一处——把 `<LanguageSwitcher />` 放进 `client/shell/user-menu.tsx`。加上 `client/locales/` 目录和 `application.ts` 里的一个字段，**模板侧总接触面是三处**。

### React 绑定用 react-i18next

`@nocobase/app-sdk/i18n/client` 直接依赖 `react-i18next`，不作为 peer。

理由是 `useTranslation` 的订阅时序、Suspense、ns 就绪判断都是坑，自己写会踩一遍——portal-sdk 现在手写 `useSyncExternalStore` 的那版已经能看出成本。`<Trans>` 的富文本插值也是白拿的能力，"点击<a>这里</a>重试"这类需求迟早会来，手写很痛苦。我们只在它之上加一层 `NamespaceScope` context 和 `defineNamespace` 绑定，代码量很小。

代价是多一个依赖，但它是 i18next 官方包、体积小、和 i18next 的版本对应关系清晰，比自研薄绑定的长期维护成本低。

## 服务端

服务端必须能自己完成翻译。这是需求里明确的一点：app 可能只提供 API 而没有前端界面，此时没有任何"前端来渲染"的机会。

### 请求级 locale

`app-server-kit` 提供 `i18nHttpMiddleware`，和现有的 `sessionHttpMiddleware`、`requestLoggingMiddleware` 并列，模板 `server/app.ts` 里加一行：

```ts
app.addHttpMiddleware(i18nHttpMiddleware);
```

决议顺序：查询参数 `?locale=` → `X-NocoBase-Locale` 请求头 → 用户 profile 的偏好 → `Accept-Language` → app 配置的默认语言。结果写进 hono context：

```ts
c.get('locale'); // 'zh-CN'
c.get('t'); // 绑定了当前 locale 和当前路由所属包 ns 的 translator
```

`c.get('t')` 的默认 ns 由中间件按注册该路由的插件包名注入，所以插件的路由处理器里 `c.get('t')('errors.notFound')` 直接命中自己的 ns，fallback 链与前端一致。

### 插件贡献服务端资源

`defineServerPlugin` 增加 `i18n` 字段：

```ts
// packages/app-plugin-workflow/server/plugin.ts
import enUS from './locales/en-US.js';
import zhCN from './locales/zh-CN.js';

export default defineServerPlugin({
  packageName: '@nocobase/app-plugin-workflow',
  i18n: {
    resources: { 'en-US': enUS, 'zh-CN': zhCN },
    dynamic: WorkflowDynamicResources,
  },
  providers: [WorkflowProvider],
  apiRoutes: [workflowApiRoutes],
});
```

服务端没有 chunk 的问题，静态资源直接内联，不需要 loader。

`dynamic` 是可选的，给"用户自定义标签"这类场景。它是一个类或函数，签名 `(app, locale) => Promise<Record<string, string>>`。i18n API 按前端请求的 ns 调用对应的 resolver 合并返回；服务端自己翻译时也会按需调用它。

### 服务端 translator

服务端没有 React context，所以走显式绑定。请求内最方便的是 `c.get('t')`。请求外——queue job、cron、webhook 回调——必须显式给 locale：

```ts
const i18n = app.container.resolve(i18nToken);
const t = i18n.forNamespace('@nocobase/app-plugin-workflow');

t('job.failed', { locale: user.appLang, name: workflow.title });
```

**locale 必须是显式参数，不能依赖任何隐式上下文。** 出站内容的语言取决于收件人，不是取决于触发这次执行的那个请求。一封发给 A 的邮件可能是 B 的操作触发的，用请求 locale 就错了。这一条要在文档和代码注释里写死。

### 错误消息

服务端直接返回翻译好的 message，同时保留结构化字段供前端按界面语言重新渲染：

```jsonc
{
  "error": {
    "code": "WORKFLOW_TRIGGER_INVALID",
    "message": "触发条件配置无效：缺少 name 字段",
    "ns": "@nocobase/app-plugin-workflow",
    "key": "errors.triggerInvalid",
    "params": { "field": "name" },
  },
}
```

`message` 用请求决议出的 locale 翻译，纯 API 调用方直接读它就够了，这是需求里"只提供 API 没有前端"的场景。`ns` / `key` / `params` 让有前端的场景可以忽略 `message`，用界面当前语言重新渲染——用户在页面上切了语言，之前收到的错误也能跟着变。SDK 提供 `useServerError(error)` 完成这个渲染，拿不到 `key` 时回落到 `message`。

抛错侧用一个统一的构造：

```ts
throw new AppI18nError('WORKFLOW_TRIGGER_INVALID', {
  ns: WORKFLOW_NS,
  key: 'errors.triggerInvalid',
  params: { field: 'name' },
});
```

翻译发生在错误序列化的时候（此时能拿到请求 locale），不是在抛出的时候。这样同一个错误对象在不同请求里能翻成不同语言，也不会在构造错误时就要求调用方知道 locale。

## Key 的智能提示

不做严格类型安全。插件写 app 的 key 是合法用法（fallback 链就是为此设计的），严格类型会把它判成错误。

但可以做补全提示：从各包的 `en-US.ts` 推导一个字面量联合类型，作为 `t()` 第一个参数的**弱约束**——用 `key: KnownKeys | (string & {})` 这种写法，已知 key 有补全，未知 key 不报错。

```ts
// defineNamespace 的返回类型带上资源类型参数
export const { t, useT } = defineNamespace<typeof enUS>(NS, resources);

t('trigger.'); // 这里有补全
t('save'); // 落到 app 的 key，不报错
```

嵌套对象转扁平点分路径的类型工具（`FlattenKeys<T>`）放在 core 里。这套是纯类型层面的，不影响运行时，也不阻塞任何用法。

跨 ns 的补全（写了 `{ ns: APP_NS }` 之后补全 app 的 key）在插件侧做不到，因为插件编译期不知道用户 app 的资源类型。这个能力只在 app 自己的代码里成立，可以后面再看。

## 落地顺序

分成能独立验证的步骤，每步都可单独合并：

1. **app-sdk 多入口改造**：tsconfig 换 `server-library.json` 并补 DOM lib，加 `./i18n`、`./i18n/client`、`./i18n/server` 三个导出，加 i18next 依赖。不含业务逻辑，只是把架子搭起来。
2. **core**：ns 注册表、locale 解析与 fallback、资源合并、i18next 实例、`FlattenKeys` 类型工具、从 portal-sdk 搬过来的表达式解析。带单测，不接任何东西。
3. **`/i18n/client`**：react-i18next 绑定、`defineNamespace`、`NamespaceScope`、`useLocale`、`LanguageSwitcher`、Refine `i18nProvider` 适配。
4. **接进 `app-client`**：`defineClientPlugin` 和 `defineClientApplication` 加 `locales` 入口；`createAppRuntime` 里做初始化；路由、provider、settings 渲染层自动包 `NamespaceScope`。
5. **模板接线**：`client/locales/`、`application.ts` 声明、用户菜单挂 switcher。此时纯前端 i18n 已经可用可演示。
6. **`/i18n/server` 加 `app-server-kit`**：中间件、`defineServerPlugin.i18n`、`i18nToken`、`/api/i18n/bootstrap` 与 `/api/i18n/preference`、app 的 `server/config/i18n.ts`。
7. **错误消息契约**：`AppI18nError`、序列化时翻译、前端 `useServerError`。
8. **改造一个真实插件做样板**：`app-plugin-workflow` 最合适，它同时有页面、服务端接口和来自数据库的动态文案。这一步会把前面所有设计问题暴露出来。
9. **收尾**：portal-sdk 转发层、registry 清理、`pnpm plugin:create` 脚手架带上 `locales/`、`pnpm i18n:check` 脚本。

第 8 步完成之前不要往其他插件推广。
