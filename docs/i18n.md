# I18n

这份文档记录 NocoBase V3 国际化方案的设计与取舍。

**日常开发不用看这里**，按用途去对应的文档：

- 写文案、加语言、组件里怎么翻译 —— [app-i18n README](../packages/app-i18n/README.md)
- 语言切换、接口、`useAppLocale` —— [app-plugin-i18n README](../packages/app-plugin-i18n/README.md)
- 插件里接入 i18n —— [插件开发快速开始](./plugin-development-quickstart.md#多语言)
- App 里写用户可见文案 —— [app-template-default AGENTS.md](../packages/app-template-default/AGENTS.md)

下面是方案本身：app（`app-template-default` 生成的用户项目）和插件（`@nocobase/app-plugin-*`）如何各自声明翻译资源，如何统一切换语言，以及前后端分别怎么用。

能力全部封装在包里。用户项目里只有自己的翻译文案和「语言切换器摆在哪」，其余机制都在包内部演进，模板升级不需要改用户代码。

## 包的划分

### `@nocobase/app-i18n`：基础能力

只提供机制。不知道「用户」「登录态」「HTTP 接口」的存在，也不注册任何路由。

```
@nocobase/app-i18n
├── .          core：同构。i18next 实例、ns 注册表、locale 决议、资源加载器管理
├── ./client   React 绑定：I18nextProvider 接线、Refine i18nProvider 适配
└── ./server   Node 绑定：请求级 translator、locale 决议中间件、按需加载
```

core 依赖 `i18next`；`./client` 依赖 `react-i18next`，`react` 是 peer；`./server` 只把 `hono` 作为 peer 引用。三个入口分开，浏览器构建不会走到 `./server`，Node 不会走到 `./client`。

包同时含 Node 与浏览器代码，tsconfig 按根 `AGENTS.md` 的混合包规则走 `server-library.json` 并本地补 DOM lib，和 `app-host` 一致。

### `@nocobase/app-plugin-i18n`：上层封装

一个常规插件，`client/` 和 `server/` 都有，做用户能看见的那部分：

- 服务端提供 `GET /api/i18n/locales`（可用语言列表）和 `POST /api/i18n/locale`（切换语言，写 session）
- 前端提供 `LanguageSwitcher` 组件和 `useLocale()` hook
- 编排完整的切换链路：写 localStorage、通知后端、切 i18next、更新 `<html lang>`

它调用 `@nocobase/app-i18n` 的方法，自己不实现任何 i18n 机制。app 想要语言切换功能就装它，不想要就不装——**翻译、ns、fallback 这些基础能力不依赖这个插件，永远可用**。

### 依赖关系

```
                @nocobase/app-i18n  (core)
                    ↑              ↑
   @nocobase/app-i18n/client   @nocobase/app-i18n/server
              ↑                              ↑
     @nocobase/app-client            @nocobase/app-server-kit
              ↑                              ↑
        app-template-default  /  @nocobase/app-plugin-*
                          ↑
              @nocobase/app-plugin-i18n
```

`app-client` 和 `app-server-kit` 依赖 `app-i18n` 并在 `defineClientPlugin` / `defineServerPlugin` 里接线，插件作者写 `locales` 字段就够了，不需要直接 import `app-i18n`。需要在组件里翻译时才 import `@nocobase/app-i18n/client`。

## Namespace

### 用包名

namespace 直接取 `packageName`，插件不需要额外声明。包名在 npm 上唯一，天然不冲突。

| 来源             | ns                                                                                        |
| ---------------- | ----------------------------------------------------------------------------------------- |
| app              | `package.json` 的 `name`，模板默认 `@nocobase/app-template-default`，用户项目是自己的包名 |
| 官方插件         | `@nocobase/app-plugin-workflow`                                                           |
| 第三方插件       | `@acme/app-plugin-crm`                                                                    |
| 基础包内置通用词 | `@nocobase/app-i18n`                                                                      |

显式写 ns 时字符串长，用常量而不是字面量。插件从自己的 locales 模块导出：

```ts
// packages/app-plugin-workflow/client/locales/index.ts
export const NS = '@nocobase/app-plugin-workflow';
```

app 的 ns 由基础包导出 `APP_NS` 常量。插件要复用 app 的翻译时写 `t('save', { ns: APP_NS })`，不用关心 app 实际叫什么——用户项目的包名是用户自己起的，插件编译期不可能知道。

### fallback 链

每个 ns 的解析顺序：

```
当前 ns  →  app ns  →  @nocobase/app-i18n
```

插件里 `t('save')` 先找自己的，没有落到 app 的，再没有落到基础包内置的通用词（保存、取消、确认、分页这类）。**插件不写任何 ns 就已经能复用 app 的词条**，需要显式指定时 `t('label', { ns: APP_NS })` 依然可用，且显式指定之后仍然继续 fallback。

实现上链是作为**有序 ns 数组**传给 `getFixedT` 的，不是走 i18next 的 `fallbackNS`——后者只读实例级配置，而这里一个实例服务所有 ns，每个 ns 的链都不一样。对插件作者没有区别，写法就是上面那样。

反过来，app 覆盖插件文案也要支持——插件某句话不合业务口径，但不想改插件源码。app 的 locale 文件给一个 `overrides` 段：

```ts
// client/locales/zh-CN.ts
export default {
  welcome: '欢迎',
  overrides: {
    '@nocobase/app-plugin-workflow': {
      trigger: { title: '触发条件' },
    },
  },
};
```

基础包在所有插件资源注册完成后，对每个被覆盖的 ns 调一次 `i18n.addResourceBundle(locale, ns, {...}, true, true)`。顺序由基础包保证。

### 默认 ns 由渲染层注入

「ns 默认不用输入」通过 `react-i18next` 原生的 `I18nextProvider` 加 `defaultNS` 实现，由 `app-client` 在渲染层调用，用户无感。

`app-client` 的每个贡献都记录了 `packageName`（`AppClientRegisteredRoute`、`AppClientRegisteredProvider`、`AppClientRegisteredSetting` 上都有这个字段），所以路由、provider、settings 渲染时自动包一层：

```tsx
// app-client 内部
<I18nextProvider i18n={i18n} defaultNS={[route.packageName, appNs, baseNs]}>
  <Page />
</I18nextProvider>
```

`defaultNS` 收的是整条链而不只是自己的 ns，同时 i18next 要配 `react.nsMode: 'fallback'`——否则 react-i18next 只取数组第一项，fallback 就断了。

插件页面里就是原生用法：

```tsx
import { useTranslation } from 'react-i18next';

const { t } = useTranslation();
t('trigger.title'); // 自己 ns 的 key
t('save'); // fallback 到 app 或基础包
t('label', { ns: APP_NS }); // 显式指定
```

**注意跨 ns 边界的组件：插件导出给 app 复用的组件，渲染时拿到的是 app 的 ns，不是插件的。** 因为 context 跟着渲染树走，不跟着代码所有权走。这类组件必须显式写 `useTranslation(NS)`。判断标准：这个组件会不会在自己插件的路由之外被渲染，会就显式写。

## 翻译资源

### 格式与嵌套

TS 模块。用户拿到的是源码级项目，TS 有类型、能推导、能写注释，也能被动态 import 直接加载。

key 允许嵌套，`A.B.C` 形式访问：

```ts
// client/locales/en-US.ts
export default {
  trigger: {
    title: 'Trigger',
    types: {
      schedule: 'Schedule',
      webhook: 'Webhook',
    },
  },
  errors: {
    notFound: 'Workflow not found',
  },
};
```

```ts
t('trigger.types.schedule'); // 'Schedule'
```

对应的 i18next 配置：`keySeparator: '.'` 开启，`nsSeparator: false` 关闭——避免 key 里的冒号被误解析成 ns，ns 一律走 options。

按语言分文件，`en-US` 是 source of truth，只写文案；结构由 `LocaleResource<typeof enUS>` 推出来，其他语言用这个类型标注，写错 key 或漏 key 都会立刻报错：

```
client/locales/
├── index.ts      locale 到 loader 的映射
├── en-US.ts      写文案，并导出 LocaleResource<typeof enUS>
└── zh-CN.ts      const zhCN: XxxResource = { ... }
```

类型从字面量推导而不是手写 interface，结构就只有一处定义。叶子会被放宽成 `string`，所以译文不会被英文原文的字面量类型卡住。

缺失的 key 由 `pnpm i18n:check` 脚本报告，不阻断开发。

### 按需加载

client 和 server 用完全一样的形式声明——locale 到 loader 的映射，值是动态 import：

```ts
// client/locales/index.ts  和  server/locales/index.ts 完全同构
export const NS = '@nocobase/app-plugin-workflow';

export default {
  'en-US': () => import('./en-US.js'),
  'zh-CN': () => import('./zh-CN.js'),
};
```

**前端**只加载当前语言。启动时并行加载所有已注册 ns 的 `en-US` 资源，用户切到 `zh-CN` 才 import 各 ns 的 `zh-CN` chunk。切走之后不卸载，再切回来不用重新加载。

**后端**首次遇到某个语言时懒加载并常驻。启动只加载默认语言，第一个 `zh-CN` 请求触发 `await import('./zh-CN.js')`，之后所有 `zh-CN` 请求直接用。

请求之外的场景——queue job、cron、webhook 回调——同样要先确保资源就绪。基础包提供 `ensureLocaleLoaded(locale)`，中间件自动调，请求外的代码必须手动调：

```ts
await i18n.ensureLocaleLoaded(user.appLang);
const t = i18n.getFixedT(user.appLang, NS);
```

漏掉这次 await 不会报错，表现是翻译静默回落到 key 或默认语言，很难发现。`@nocobase/app-i18n/server` 的类型注释里要写死这条。

按需的维度是**语言，不是 namespace**。前端启动时会加载所有已注册插件当前语言的资源，哪怕用户不打开那个插件的任何页面。这是有意的：侧边栏要渲染全部插件路由的 label，而 label 就在各插件自己的 ns 里，ns 级按需要成立就得把导航文案和页面文案拆成两份资源，插件作者多维护一个文件。locale 是纯文本且并行加载，这点体积不值得换那份复杂度。

前端 loader 的 key 必须是运行时取值。写成 `locales['en-US']()` 这样的字面量索引会让其他语言在构建时被 tree-shake 掉，产物里根本没有那个 chunk。

### 构建产物

`() => import('./zh-CN.js')` 是纯动态 import，打包器天然把每个 locale 切成独立 chunk，文件名带内容哈希。所以业务代码改动不会动 locale chunk 的文件名，改一个语言也不会波及同插件的其他语言或别的插件——用户升级后浏览器只重新下载真正变了的那几个 locale 文件。这个性质是上面的声明形式自带的，不需要额外配置。

默认产出的 chunk 只带语言名（`en-US-BaqwdymH.js`），多个插件的文件混在一起分不清归属。`@nocobase/dev-config` 的 portal preset 统一配置 `chunkFileNames`，把 ns 的包名加进路径：

```
assets/locales/app-template-default.en-US-BaqwdymH.js
assets/locales/app-plugin-workflow.en-US-COhCuYK9.js
assets/locales/app-plugin-workflow.zh-CN-SJx9boDC.js
```

重命名不参与内容哈希计算，纯粹是可读性收益。放在 preset 里是因为这属于产物组织方式而非业务选择；app 想改可以在自己的 `vite.config.ts` 里覆盖。

## 前端

### 插件声明资源

`defineClientPlugin` 增加 `locales` 入口，和现有四个 loader 平级：

```ts
// packages/app-plugin-workflow/client/plugin.ts
export default defineClientPlugin({
  packageName: '@nocobase/app-plugin-workflow',
  locales: () => import('./locales/index.js'),
  bootstrap: () => import('./bootstrap.js'),
  routes: () => import('./routes.js'),
  settings: () => import('./settings.js'),
  providers: () => import('./providers.js'),
});
```

`app-client` 内部调 `@nocobase/app-i18n` 的注册方法，用 `packageName` 作为 ns 登记这批 loader。**插件作者要做的只有两件事：加一个 `locales` 字段，写 locale 文件。**

app 走 `defineAppRuntime`，写法相同。基础包把 Runtime Definition 认作 application contribution，并将它的 ns 记为 app ns，也就是 `APP_NS` 和 fallback 链第二级指向的东西。

### 初始化时机

i18n 初始化在 `resolveAppRuntime()` 里完成——它本身是 async，且在 `root.render` 之前执行：

1. 解析初始 locale：`localStorage` → `navigator.language` → 默认值
2. 收集所有 contribution 声明的 ns 和 loader
3. 并行加载这些 ns 的当前 locale 资源
4. `i18n.init()`
5. 才 `root.render`

代价是首屏多一批并行的动态 import，都是本地 chunk。换来零闪烁，第一帧就是正确语言，不需要 Loading 遮罩。

这一步**不依赖后端**，只读 localStorage。没装 `app-plugin-i18n` 的应用照样能正常显示默认语言。

### 语言切换

`@nocobase/app-plugin-i18n/client` 提供：

```tsx
import { useLocale, LanguageSwitcher } from '@nocobase/app-plugin-i18n/client';

const { locale, locales, setLocale, switching } = useLocale();
```

`setLocale(next)` 的完整链路：

1. `localStorage.setItem('nocobase.locale', next)`，先写，保证刷新后不丢
2. 并行加载所有已注册 ns 的 `next` 语言资源
3. `POST /api/i18n/locale { locale: next }`，通知后端写 session
4. `i18n.changeLanguage(next)`，i18next 广播 `languageChanged`
5. 更新 `<html lang>` 和 `<html dir>`

第 2 步是「所有 ns 一起等」，所以切换是原子的，不会出现半中半英的中间态。第 3 步失败时不阻塞前端切换，但要在控制台警告——此时前端已经是新语言而后端还是旧的，这是可感知的不一致（比如接口返回的错误消息语言不对），刷新页面会通过下面的启动同步自愈。

**插件响应语言切换不需要任何插件侧代码**：所有 ns 共用同一个 i18next 实例，`useTranslation` 底层订阅 `languageChanged`，插件组件自然重渲染。

### 启动时的前后端同步

localStorage 是前端的事实来源，session 是后端的。两者可能不一致——用户换了浏览器、session 过期、或者在另一个标签页切过语言。

所以应用启动时，如果 localStorage 里有值，无条件发一次 `POST /api/i18n/locale` 把后端对齐。这个请求不阻塞渲染，前端已经用 localStorage 的值渲染完了。

### 模板的接触面

模板里的接线只有三处：

1. `client/locales/` 目录，放 app 自己的文案
2. `client/runtime.ts` 里加 `locales` 字段
3. `client/shell/user-menu.tsx` 里放 `<LanguageSwitcher />`

加上 `client/plugins.ts` 和 `server/plugins.ts` 里注册 `app-plugin-i18n`，这些都是 `pnpm plugin:register` 自动写的。

## 服务端

### 请求级 locale

`@nocobase/app-i18n/server` 提供 `i18nHttpMiddleware`，和 `sessionHttpMiddleware`、`requestLoggingMiddleware` 并列，模板 `server/app.ts` 加一行：

```ts
app.addHttpMiddleware(i18nHttpMiddleware);
```

决议顺序：session 里的 locale → `Accept-Language` → 配置的默认语言。中间件确保资源就绪后写进 hono context：

```ts
const locale = resolveLocale(c);
await ensureLocaleLoaded(locale);
c.set('locale', locale);
c.set('t', i18n.getFixedT(locale, ns));
```

`c.get('t')` 的默认 ns 按注册该路由的插件包名注入，插件路由处理器里 `c.get('t')('errors.notFound')` 直接命中自己的 ns，fallback 链和前端一致。

中间件必须在 session 中间件之后注册，否则读不到 session。

### 插件声明资源

`defineServerPlugin` 增加 `locales` 字段，和 client 完全同构：

```ts
// packages/app-plugin-workflow/server/plugin.ts
export default defineServerPlugin({
  packageName: '@nocobase/app-plugin-workflow',
  locales: () => import('./locales/index.js'),
  providers,
  routes,
});
```

`app-server-kit` 在启动时把这些 loader 注册给 `@nocobase/app-i18n`，按 `packageName` 归入对应 ns，实际加载推迟到该语言第一次被用到。

### 语言切换接口

由 `@nocobase/app-plugin-i18n/server` 提供，不在基础包里：

```
GET  /api/i18n/locales    → { defaultLocale, locales: [{ locale, label }] }
POST /api/i18n/locale     { locale } → 写 session，200
```

`POST` 要校验 locale 在允许列表内，否则 400——这是外部输入。

locale 存在 session 里，所以**同一账号的多个标签页会互相覆盖**：标签页 A 切到中文，标签页 B 的后续请求也会拿到中文的服务端消息，而 B 的界面还是英文。下面错误消息的结构化字段能让前端绕开这个不一致。

### 可切换的语言列表

由 `@nocobase/app-plugin-i18n` 的插件 options 传入，前后端各写一次：

```ts
// client/plugins.ts
i18n({ locales: ['en-US', 'zh-CN'], defaultLocale: 'en-US' });

// server/plugins.ts
i18nPlugin({ locales: ['en-US', 'zh-CN'], defaultLocale: 'en-US' });
```

前后端各写一遍有不一致的风险，靠文档约束。等上层 config 能力就绪后换成 app 的 `server/config/i18n.ts` 单一来源，前端通过 `GET /api/i18n/locales` 拿——**接口形态现在就按最终形态定，那次替换只改底层实现，不改调用方**。

### 服务端翻译

服务端要能自己完成翻译：app 可能只提供 API 而没有前端界面，此时没有任何「前端来渲染」的机会。

请求内用 `c.get('t')`。请求外——queue job、cron、webhook——必须显式给 locale：

```ts
await i18n.ensureLocaleLoaded(user.appLang);
const t = i18n.getFixedT(user.appLang, NS);
t('job.failed', { name: workflow.title });
```

**locale 必须是显式参数，不能依赖任何隐式上下文。** 出站内容的语言取决于收件人，不取决于触发这次执行的请求。一封发给 A 的邮件可能是 B 的操作触发的，用请求 locale 就错了。这条要在代码注释里写死。

### 错误消息

服务端返回翻译好的 `message`，同时带上结构化字段：

```jsonc
{
  "error": {
    "code": "WORKFLOW_TRIGGER_INVALID",
    "message": "触发条件配置无效：缺少 name 字段",
    "ns": "@nocobase/app-plugin-workflow",
    "key": "errors.triggerInvalid",
    "params": { "field": "name" },
  },
}
```

`message` 用请求决议出的 locale 翻译，纯 API 调用方直接读它就够。`ns` / `key` / `params` 让有前端的场景可以忽略 `message`，用界面当前语言重新渲染——用户在页面上切了语言，之前收到的错误也能跟着变，也不受 session 多标签页覆盖的影响。

抛错侧统一构造：

```ts
throw new AppI18nError('WORKFLOW_TRIGGER_INVALID', {
  ns: NS,
  key: 'errors.triggerInvalid',
  params: { field: 'name' },
});
```

翻译发生在错误序列化时，此时才能拿到请求 locale。这样同一个错误对象在不同请求里能翻成不同语言，构造错误时也不需要知道 locale。

## Key 的智能提示

不做严格类型安全。插件写 app 的 key 是合法用法，fallback 链就是为此设计的，严格类型会把它判成错误。

做弱约束的补全：从各包的 `en-US.ts` 推导字面量联合类型，用 `key: KnownKeys | (string & {})` 这种写法，已知 key 有补全，未知 key 不报错。需要一个把嵌套对象转成点分路径的类型工具，放在 core 里：

```ts
type FlattenKeys<T> = /* 'trigger' | 'trigger.title' | 'trigger.types.schedule' | ... */
```

纯类型层面，不影响运行时，也不阻塞任何用法。

跨 ns 的补全（写了 `{ ns: APP_NS }` 后补全 app 的 key）在插件侧做不到，插件编译期不知道用户 app 的资源类型。这个能力只在 app 自己的代码里成立。

## 现有代码的处置

划一条线：**运行时机制不 materialize 进用户项目，只有用户可能想改的 UI 才 materialize。** 语言切换器归插件，它的形态由插件 options 控制就够；用户真要完全自定义，`useLocale()` 是公开的。

| 现有                        | 处置                                                                                                                                                                                            |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `app-portal-sdk/src/i18n/*` | 保留，标记为 deprecated。它服务的是 Portal 架构的应用（`packages/hub` 仍在用），维持自己的 i18next 实例直到 Portal 模板下线。**一个应用里两套不能混用**：资源会各持一半，语言切换也只有一边响应 |
| `registry/nocobase-i18n/`   | 保留不动。整个 `registry/` 目录都还是 Portal 的 `AppExtension` ABI，新架构的 `client/` 不引用它，也不会被 materialize 进来。它随 Portal 模板一起退场，不单独拆                                  |
| `packages/hub/`             | 不改。hub 仍是 Portal 架构，用 flat dotted key（`'shell.workspace'`），迁移是它自己的事                                                                                                         |

## 落地顺序

分成能独立验证的步骤，每步都可单独合并：

1. **`@nocobase/app-i18n` core**：i18next 实例、ns 注册表、loader 管理、locale 决议与 fallback、`ensureLocaleLoaded`、`FlattenKeys` 类型工具、从 portal-sdk 搬来的表达式解析。带单测，不接任何东西。
2. **`./client`**：`react-i18next` 接线、Refine `i18nProvider` 适配、`APP_NS`。
3. **接进 `app-client`**：`defineClientPlugin` 和 `defineAppRuntime` 加 `locales` 入口；`resolveAppRuntime` 里做初始化；路由、provider、settings 渲染层自动注入 `defaultNS`。
4. **模板前端接线**：`client/locales/`、`runtime.ts` 声明，以及 `dev-config` portal preset 的 `chunkFileNames`。此时纯前端多语言可用可演示，还没有切换器。
5. **`./server` 加 `app-server-kit`**：`i18nHttpMiddleware`、`defineServerPlugin.locales`、按需加载。
6. **`@nocobase/app-plugin-i18n`**：两个接口、`useLocale`、`LanguageSwitcher`、完整切换链路、启动同步。此时功能闭环。
7. **错误消息契约**：`AppI18nError`、序列化时翻译、前端按 `ns` 和 `key` 重渲染。
8. **改造 `app-plugin-workflow` 做样板**：它同时有页面、服务端接口和跨 ns 复用的组件，能把前面的设计问题暴露出来。
9. **收尾**：portal-sdk 转发层、registry 清理、`create-plugin` 模板带上 `locales/`、`pnpm i18n:check` 脚本。

第 8 步完成之前不要往其他插件推广。
