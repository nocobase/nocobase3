# Application Development

This page covers components, business data, and APIs for application developers customizing mail features. To build a basic mail center with AI, start with the [Quick Start](./quick-start.md).

## Define the integration scope

Decide whether mail belongs on a standalone page or a business detail page, which roles can use it, and which account management and log features are needed. Personal mail operations must remain limited to accounts owned by the current user. Managing all users' mail requires separate permission.

To display correspondence on a customer detail page, define how messages relate to customers and how they are filtered. Passing template variables only affects composed content; it does not automatically link messages to customers or filter their correspondence.

## Use the plugin skill

Have the application agent read `.agents/skills/nocobase-app-plugin-mail/` from the installed version and use the plugin's interfaces to implement the integration. If the plugin is registered but the skill is missing, run this from the application root:

```bash
pnpm plugin:skills:sync
```

This directory is generated by synchronization; do not edit it directly. If a custom application has not registered Mail, run `pnpm plugin:register mail`, then `pnpm migrate` to create the required tables. Configure providers as described in [Mailbox Setup](./configuration.md).

## Reuse client components

For a complete workspace, use `MailWorkspacePage` exported by `@nocobase/app-plugin-mail/client`. For account connections, signatures, templates, and labels, refer to the public `MailAccountConnector`, `MailSignatureManager`, `MailTemplateManager`, and `MailLabelManager` components and connect them to your application's data and interactions.

Place components within the application's client service and permission contexts, and register the Mail Client plugin before rendering. React code obtains the current application's client with `useMailClient()`. Non-React code can resolve `mailClientToken`. Do not create and share a mail client at module scope.

### Development examples

These addresses provide development and component integration examples. Paths are relative to the application mount point. For example, when mounted at `/main`, the mail center is at `/main/dev/mail/center`.

| Page                   | Reference                                                     |
| ---------------------- | ------------------------------------------------------------- |
| `/dev/mail/center`     | Mail workspace, account filters, conversations, and composing |
| `/dev/mail/accounts`   | Account connections, signatures, templates, and labels        |
| `/dev/mail/send`       | Regular and separate sending, and drafts                      |
| `/dev/mail/logs`       | Send, bulk send, and synchronization results                  |
| `/dev/mail/management` | All-user mail filtering and batch operations                  |

The administrator account overview at `/settings/mail/accounts` provides a read-only view of all users' connected accounts.

Development pages are excluded from production builds. Check all links in production pages and the return location after OAuth. The plugin currently returns to the development account page by default, so adding the mail workspace alone does not complete production account connection support.

## Pass business records

Use `MailWorkspacePage`'s `templateVariables` to supply values from business records:

```tsx
import { MailWorkspacePage } from '@nocobase/app-plugin-mail/client';

export function CustomerMail() {
  return (
    <MailWorkspacePage
      templateVariables={{ record: { customer: { name: 'Alex' } } }}
    />
  );
}
```

When applying a template, `{{record.customer.name}}` becomes `Alex`. Pass only permitted data from the current record. Variables without a matching value remain unchanged and should be checked before sending.

## Send mail from business code

Resolve the service through `mailServiceToken` and use `MailService.sendMessage()`, or call `POST /api/mail/messages/send`. Personal APIs check authentication, mail workspace permission, and account ownership. Server-side integrations should preserve the same access boundaries.

Reuse a stable `idempotencyKey` for the same business send operation. Reusing a key with different content is rejected. After a timeout, query the original submission result rather than sending again with a new key. A provider submission result of `unknown` should put the business operation into a state requiring confirmation.

For system notifications, use [Notifications](../notification.md). Use the mail service when reading users' mailboxes or sending through their connected accounts.

## Extend providers and credential storage

Gmail, Microsoft 365, and IMAP/SMTP are built in. Register other protocol providers through `mailProviderRegistryToken` in an extension plugin. Refer to the current plugin's exported types and skill for the interfaces.

The default credential store saves authorization data as plain JSON in the database. If your application requires encryption at rest, provide a replacement implementation of `mailCredentialVaultToken` before registering Mail Core. Do not put mailbox passwords in frontend code or commit them to the repository.

## Verify the integration

Have the agent run the application's lint, typecheck, test, and build checks and provide verification results for these scenarios:

- Production pages can connect accounts, and OAuth success or failure returns to an accessible page.
- Regular users cannot read or modify other users' accounts, messages, or attachments.
- Synchronization, reading, replying, attachments, draft recovery, and scheduled sending work as expected.
- Templates use the current record, and missing variables can be identified before sending.
- Logs distinguish failures, partial delivery, and uncertain results; retries do not duplicate successful sends.
