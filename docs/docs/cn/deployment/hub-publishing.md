# 使用 Hub 发布应用

本页介绍向已有 Hub 发布应用的流程。尚未搭建平台时，先阅读[部署 Hub 平台](./hub)。

## 发布过程中的三个概念

| 名称               | 含义                                                | 以 CRM 为例                   |
| ------------------ | --------------------------------------------------- | ----------------------------- |
| 应用（App）        | Hub 中持续管理的对象，拥有固定 ID                   | CRM 应用，ID 为 crm           |
| 发布包（Release）  | 上传后保存的不可变构建制品                          | 本次构建的 CRM 代码与生产依赖 |
| 部署（Deployment） | 选择一个 Release 和运行配置，让它在服务器运行的操作 | 把本次构建部署到 CRM          |

同一个应用可以上传多个 Release，并保留多次部署记录。上传与部署是两个独立操作；Runtime 表示应用当前的运行实例。

## 准备发布

### 1. 登录 Hub

使用具有目标应用管理权限的账号登录 Hub，例如 `https://apps.example.com/hub/`。通过 CLI 发布时，还需配置发布 API Key，见下方[通过 CLI 部署](#通过-cli-部署)。

### 2. 创建应用

在 Hub 中创建应用，记录应用 ID 和访问地址。已有应用直接使用原记录，无需重复创建。

| 信息         | 示例                            | 用途                       |
| ------------ | ------------------------------- | -------------------------- |
| 应用 ID      | `crm`                           | CLI 发布时指定目标应用     |
| 应用访问地址 | `https://apps.example.com/crm/` | 部署后访问业务应用         |
| 应用路径     | `/crm`                          | 构建时设置 `APP_BASE_PATH` |

### 3. 构建部署包

在业务应用项目根目录执行构建，使用 Hub 中显示的应用路径。例如，应用路径为 `/crm`，Hub 运行环境为 Linux x64、glibc 和 Node.js 24 时：

```bash
APP_BASE_PATH=/crm pnpm build --target linux-x64 --node-version 24 --tar
```

构建成功后生成 `storage/exports/dist.tar.gz`，后续通过管理页面或 CLI 上传此文件。

`--target` 应与 Hub 所在的运行环境一致。例如，Linux ARM64 使用 `linux-arm64`；不能直接采用开发电脑的平台。完整构建说明见[构建部署包](./standalone#构建部署包)。

## 通过管理页面部署

1. 打开目标应用详情，进入 Release 与部署页面。
2. 上传构建包，核对显示的版本和 Release。上传不会切换当前运行版本。
3. 点击部署，选择要运行的 Release。
4. 选择配置方式，按下面的规则填写或复用运行配置。
5. 审阅后提交，等待部署记录显示成功；失败时查看该次部署日志。
6. 打开应用地址，验证登录、数据库内容和实际业务功能。

首次采用文件配置时，用 Release 模板作为起点，填写生产数据库、文件存储及外部服务参数；Hub 会为缺失、空白或示例占位的 auth.secret、session.secret 生成密钥，保留已有有效值。

已有应用再次部署默认沿用当前配置，新 Release 模板不会自动覆盖它。若新增必填配置，需要审阅模板差异并补充。外部配置模式要求应用已接入可用的外部配置来源。

## 通过 CLI 部署

在 Hub 创建发布 API Key，限定目标 App 和需要的上传、部署权限。API Key 的权限还受创建者当前权限和应用归属约束。凭证通过 CI secret 或本地受保护环境配置，避免放在命令参数、版本库或日志中。

在业务项目根目录的未入库 `.env` 或终端环境中设置：

```dotenv
HUB_URL=https://apps.example.com/hub
HUB_APP_ID=crm
HUB_API_KEY=REPLACE_WITH_PRIVATE_PUBLISHING_KEY
```

CLI 配置优先级为显式参数、进程环境、App 根目录 `.env`；此发布配置不加载 `.env.local`。以下两组流程二选一。

**上传后单独部署：**

```bash
pnpm nocobase app upload --json
pnpm nocobase app deploy --release-id <RETURNED_RELEASE_ID> --wait --json
```

**上传并部署，显式提供首次运行配置：**

```bash
pnpm nocobase app upload --deploy --config ./runtime.yml --wait --json
```

默认上传 `storage/exports/dist.tar.gz`，其他路径用 `--file`。已单独上传的 Release 使用 `app deploy` 部署；对同一包补跑 `upload --deploy` 会返回冲突。

| 情况                                        | 行为                                                       |
| ------------------------------------------- | ---------------------------------------------------------- |
| 不传 `--config`，存在当前配置               | 沿用当前 Hub 配置                                          |
| 首次部署，没有可复用配置                    | 沿用 Release 模板初始化规则，部署前核对完整性              |
| 传 `--config`                               | 替换配置文档，经既有密钥处理和 YAML 校验，不合并任意旧字段 |
| 只 upload，不带 `--deploy`，却传 `--config` | 参数错误                                                   |
| 网络重试                                    | 保持同一幂等键及请求内容，查询或复用原操作                 |
| 有意重部署相同 Release                      | 用 `app deploy` 并指定新的 `--idempotency-key`             |

配置文件必须为非空 UTF-8 YAML，最大 1 MiB，路径相对于 App 根目录。配置不写入 Release，不修改原始构建包。

### 等待结果与自动化发布

部署命令默认等待最终结果，默认超时 600 秒；`--no-wait` 仅等待受理。CI 同时检查退出码和 `result.operationStatus`。

| 退出码 | 含义                                      |
| ------ | ----------------------------------------- |
| `0`    | 操作成功；使用 `--no-wait` 时只表示已受理 |
| `1`    | Hub 拒绝请求或部署失败                    |
| `2`    | 本地参数或文件错误                        |
| `3`    | 网络错误、超时或结果未确认                |

结果未确认时先查看 Hub 部署记录，网络重试沿用原幂等键。确认部署失败后重新发起部署，应使用新的幂等键。

## 更新、启停与回滚

### 更新应用

1. 在应用项目中构建新的部署包，上传到 Hub。
2. 选择新 Release，核对运行配置；新版本新增的必填配置需要补充。
3. 涉及数据库变更时，完成备份后再发起部署。
4. 查看部署结果，并访问应用确认功能正常。

部署失败时查看该次部署日志；部署成功后的业务异常查看应用运行日志。应用版本替换期间会中断服务。

### 启动与停止

在应用详情中操作：

| 操作 | 结果                                                         |
| ---- | ------------------------------------------------------------ |
| 停止 | 应用停止服务，保留当前部署、配置和数据；Hub 重启后仍保持停止 |
| 启动 | 使用当前部署和配置恢复运行                                   |

应用设置中可以选择启动策略：默认随 Hub 启动，也可设置为首次访问时启动。启动策略适用于已启用的应用，不会自动启动被手动停止的应用。

### 回滚版本

在部署历史中选择一次成功的部署，发起回滚。Hub 会使用该次部署对应的 Release 创建新的部署记录，可在记录中查看结果。

回滚前确认以下两点：

- **运行配置**：不会自动恢复当时的配置内容。文件配置模式下，未提供新内容时优先沿用当前配置，需要确认它与旧版本兼容。
- **数据库**：回滚应用版本不会撤销数据库变更或业务数据写入。若旧版本与当前数据库不兼容，应按[备份恢复流程](./operations#备份与灾难恢复)处理。

### 移除应用

移除会删除应用记录、Release、部署历史、配置和应用数据卷。仅需暂停服务时使用“停止”；确认不再需要该应用并完成必要备份后，再执行移除。
