# 备份恢复与排障

## 备份与灾难恢复

### 备份内容

| 部署方式 | 必须成套保留的内容                                                                                   |
| -------- | ---------------------------------------------------------------------------------------------------- |
| 独立应用 | 部署包或镜像 digest、实际配置与密钥、数据库、上传文件和其他持久存储、代理与服务配置                  |
| Hub 平台 | Hub 版本、平台配置与密钥、Hub 数据库、应用发布包、运行配置、各应用数据目录、外部业务数据库与对象存储 |

Hub 使用本地存储时可整体备份指定 storage 根目录，但外部数据库和外部对象存储需单独纳入一致性方案。当前重启恢复还依赖已解压的应用版本目录。整体备份 storage 可一并保留；只恢复数据库、配置和数据文件时，可能需要重新部署对应的 Release。

Hub auth.secret 还参与可恢复发布凭证的加密，需稳定保存并与数据库配套备份。部署与运行日志按保留期归档，便于定位故障时间。

### 备份时机与恢复顺序

升级和重要迁移前完成备份，并定期演练恢复。SQLite 不应在写入期间只复制主数据库文件；使用数据库支持的一致性备份方法，或停止所有写入者后备份相关文件。外部数据库使用其原生备份工具。

恢复时先停止目标服务，准备与备份匹配的版本和运行环境，再恢复数据库、文件、配置与原密钥，确认路径和权限，最后启动并验证。Hub 还需核对 Host、当前部署和每个业务应用。应用自身使用外部数据库时，应确保平台状态与该库恢复时间一致。

验收包括记录数量或关键业务记录、文件下载、登录、权限隔离、工作流、通知和重启后的持久性。不要在数据尚未恢复时启动新版本并让自动迁移改写备份目标。

## 故障排查

| 现象                           | 优先检查                                     | 处理方向                                                    |
| ------------------------------ | -------------------------------------------- | ----------------------------------------------------------- |
| 找不到部署包                   | 当前目录、模板版本、构建输出                 | 当前默认路径为 storage/exports/dist.tar.gz，必要时用 --file |
| 原生模块加载失败               | 架构、libc、Node ABI                         | 以目标平台重建，不能直接复制开发机依赖                      |
| 启动后出现空数据库             | filename、部署根目录、挂载点                 | 确认真实数据路径后停机纠正，不初始化覆盖旧库                |
| SQLite 或日志无法写入          | 运行 UID/GID、目录所有权、挂载权限           | 只修正应用专用持久目录权限                                  |
| 首页正常，刷新子页面或资源 404 | APP_BASE_PATH、构建路径、代理路径            | 保留挂载前缀，核对构建与运行配置                            |
| 登录回调或 WebSocket 失败      | origin、HTTPS、转发头、Upgrade               | 检查对外 origin 和代理协议信息                              |
| Hub 首页根路径 404             | 实际访问 URL                                 | 访问 /hub/，不要仅访问域名根路径                            |
| Hub 应用访问 503 / 502         | Host 是否就绪、连接失败、Host 日志           | 检查受管 Host 与应用状态，不只看 Hub 进程                   |
| Release 上传 413               | 代理限制与 Hub 256 MiB 限制                  | 调整代理并核对制品体积，不能只提高代理限制                  |
| 发布 401 / 403                 | Key 有效期、绑定 App、权限、创建者权限       | 更正凭证范围，不授予无关全局权限                            |
| 发布 409                       | 相同幂等键是否改变请求；Release 是否仅上传过 | 检查原操作，已上传 Release 使用 deploy                      |
| CLI 超时但页面显示运行中       | 部署记录与实际 Runtime                       | 先确认结果，避免重复发起新操作                              |
| 配置修改后升级丢字段           | --config 是替换文档                          | 提交完整目标配置并审阅差异                                  |
| 回滚后仍无法启动               | 数据库迁移兼容性、实际配置                   | 必要时执行数据库、配置和代码的配套恢复                      |

Hub 重启后，应用恢复在后台执行。管理页面可访问时，设置为随平台启动的应用（eager）可能仍在启动；检查目标应用的运行状态和日志。按需启动的应用（lazy）会在首次访问时激活。

日志从外到内检查：反向代理日志 → systemd journal 或容器日志 → Hub 部署日志 → Host 日志 → 应用运行日志。Hub 默认目录相对于显式设置的持久根目录如下；实际可由配置覆盖。

```text
hub/logs/deployments/               部署操作日志
hub/logs/app/                       Hub 自身日志
host/logs/host/                     Host 日志
host/logs/child-output/             Host 子进程输出
apps/volumes/<appId>/storage/logs/   业务应用运行日志
```

## 生产验收清单

正式上线前，按以下清单验证部署结果。

- [ ] 记录实际应用、Hub、Node、镜像版本或 digest，以及构建目标。
- [ ] 配置和数据位于持久目录，运行身份有正确权限。
- [ ] 初始管理员密码已更换，密钥未进入制品、版本库或公共日志。
- [ ] HTTPS、页面刷新、资源、登录、API 与 WebSocket 正常。
- [ ] 普通用户的数据与操作权限在服务端生效。
- [ ] 数据库迁移与 seeds 的执行结果符合预期。
- [ ] 业务记录、上传文件在进程重启及容器重建后仍保留。
- [ ] Hub 模式下，平台重启后逐个确认业务应用就绪。
- [ ] 日志有保留策略，磁盘容量可监测。
- [ ] 备份可恢复，升级失败时有已验证的处理步骤。
- [ ] 再次执行相同部署配置的启动操作，不产生重复实例或重置数据。
