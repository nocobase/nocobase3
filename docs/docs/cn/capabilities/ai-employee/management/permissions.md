# AI 员工可见性和权限

AI 员工能否被用户使用，至少受到员工状态、模型状态、角色权限和工具权限共同影响。只在员工提示词中写“不要访问某数据”不够，真正的授权必须由服务和工具代码执行。

## 员工可见性

面向业务用户的员工应当：

- 使用业务类别
- 处于启用状态
- 绑定已启用的模型
- 只暴露给需要使用它的角色
- 不包含开发环境专用能力

开发用途员工只应该出现在开发或管理场景，不要放进业务 Portal 或普通用户的聊天选择器。

## 工具权限

工具的默认权限决定 Agent 调用前是否需要用户确认：

| 场景                       | 推荐权限                   |
| -------------------------- | -------------------------- |
| 读取当前用户有权访问的数据 | `ALLOW` 或按风险使用 `ASK` |
| 修改业务记录               | `ASK`                      |
| 发送通知、提交审批或导航   | `ASK`                      |
| 删除数据或不可逆操作       | `ASK`，并在工具内再次确认  |

`ASK` 不是前端装饰。工具真正执行前，运行时必须暂停并等待用户决定。

## 给 Agent 的权限要求

你可以这样要求 Agent 实现一个安全的业务工具：

```text
实现订单查询工具时：
- 只允许查询当前用户有权限访问的订单
- 不接受模型传入的 userId 作为授权依据
- 业务写操作必须使用 ASK
- 返回值只包含当前任务需要的字段
- 添加未授权、订单不存在和正常查询三个测试
```

## 排查“看不到员工”

如果管理员能看到员工，但普通用户看不到，检查：

1. 员工是否启用
2. 员工类别是否适合当前业务场景
3. 当前用户角色是否有员工访问权限
4. 员工绑定的模型是否启用
5. 页面上的聊天组件是否使用了正确的 `username`

如果员工能看到但工具调用失败，优先检查工具的执行位置、权限、schema 和 actor 授权逻辑。

:::warning 注意

不要为了让员工出现在列表中而把工具设为 `GENERAL` 或扩大角色权限。先判断员工和工具真正需要的可见范围。

:::
