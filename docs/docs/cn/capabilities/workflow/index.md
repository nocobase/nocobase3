# 概览

NocoBase 3 工作流用于实现具有独立生命周期的业务过程：每次业务事件产生一条运行记录，系统在后台按版本执行，并保存每一步的结果、错误和日志。

在 NocoBase 3 中，工作流由应用 Agent 在源码中编写。你只需要用自然语言描述业务、审核 Agent 的方案和验证证据；业务管理员在界面中启用工作流、调整参数、手动运行和查看执行记录。

想马上体验，直接看[快速开始](./quick-start.md)。

## 什么时候使用工作流

判断标准只有一条：**业务过程是否需要一个独立、持久化、可观测的生命周期**。常见信号：

- 管理员需要看到每次处理走了哪条路径、停在哪一步；
- 流程有多个具有业务意义的阶段，并根据结果进入不同路径；
- 需要后台可靠执行、重复事件去重、整体超时；
- 流程需要版本化，历史运行必须按当时的版本解释；
- 管理员需要在不改代码的情况下调整少量业务参数，例如阈值。

典型场景：订单履约、客户入驻审核、库存补货、报价风险评估、定时生成经营报表。

以下情况更适合普通类型化代码：

- 一次请求内就能完成的查询或计算；
- 必须在同一个数据库事务中完成的原子写入；
- 以算法或数据转换为主、不需要独立运行记录的逻辑；
- 失败时只需向调用方返回错误，不需要持续观测。

代码行数多、调用了多个函数、需要异步或包含条件分支，本身都不是使用工作流的理由。拿不准时，把业务交给 Agent，让它先判断并说明理由。

## 工作流与业务代码如何分工

| 工作流负责                   | 普通业务代码负责         |
| ---------------------------- | ------------------------ |
| 业务阶段、执行顺序和条件路径 | 数据校验、查询和写入     |
| 流程级状态、版本和运行记录   | 计算、数据转换和领域规则 |
| 后台调度、事件去重和整体超时 | 数据库事务和唯一性约束   |
| 协调多个有独立意义的业务动作 | 外部系统客户端和具体集成 |

例如库存补货工作流负责“计算缺口 → 判断是否需要补货 → 创建补货记录或记录库存充足”这条路径，库存读取、缺口计算和补货写入仍由应用中的 Service 完成。

## 人与 Agent 如何协作

这里的“应用 Agent”指在应用目录中工作的编码 Agent，例如 Claude Code 或 Codex。工作流插件随包发布了名为 `nocobase-app-plugin-workflow` 的 Skill，会同步到应用的 `.agents/skills/`，Agent 通过它掌握当前版本的工作流写法和操作规范。

| 角色       | 负责什么                                                                               |
| ---------- | -------------------------------------------------------------------------------------- |
| 应用开发者 | 描述业务目标、规则和副作用；审核选型、流程阶段和风险；验收检查、测试和运行证据         |
| 应用 Agent | 检查现有数据结构、Service 和插件能力；编写工作流和业务代码；运行检查、测试、构建并报告 |
| 业务管理员 | 启用、停用或切换版本；设置开放的参数；手动运行；查看执行记录并反馈异常                 |

你不需要先学会工作流 DSL 再描述需求。DSL 参考是给审阅代码的人查阅的，编写细节以 Skill 为准。

## 当前能力与边界

工作流插件内置三种节点：

- **Run**：执行一个业务动作，例如计算、读写数据、调用 Service；
- **Condition**：根据布尔判断进入“是”或“否”分支；
- **Terminate**：从主路径或分支中提前结束整个流程。

在此基础上，工作流还提供：队列中异步执行、按事件标识去重、整体超时、版本与运行记录、节点级诊断，以及可选的输入和参数自定义表单。

触发方式有三种：业务代码调用 Workflow Service、定时任务的内置 `workflow` 执行目标，以及管理员手动运行，见[触发与扩展 API](./reference/service-api.md)。

以下能力默认不提供：

- **持久暂停与恢复**：人工审批、等待外部回调、补充资料后继续等，需要应用安装了提供相应节点的插件，或开发可复用的自定义节点；
- **循环、子流程和任意连线**：流程结构是“顺序 + 条件分支”的树；
- **界面设计器**：管理界面中的流程图是只读的，流程结构只能在源码中修改。

## 术语

| 术语               | 含义                                                                    |
| ------------------ | ----------------------------------------------------------------------- |
| 工作流包           | 应用 `workflows/` 下的一个子目录，包含 `workflow.ts` 和它引用的处理模块 |
| 工作流 key         | 工作流包的目录名，业务代码触发工作流时使用的稳定标识                    |
| 节点 / Instruction | 流程中的一个步骤。Instruction 是节点类型的实现，例如 Run、Condition     |
| 处理函数           | Run 和 Condition 节点引用的服务端模块，导出名为 `run` 的函数            |
| 输入               | 每次触发时传入的数据，例如商品 ID                                       |
| 管理员参数         | 管理员在界面中调整的少量配置，例如目标库存                              |
| 版本               | 工作流定义的一次修订。每次运行固定使用开始时的版本                      |
| Artifact           | 构建产生的不可变工作流产物，部署后由运行时加载                          |
| 运行（执行）       | 一次业务事件触发的一次工作流执行，保存输入、状态和各节点记录            |
| eventKey           | 一次业务事件的身份。相同 eventKey 的重复触发只产生一次运行              |
