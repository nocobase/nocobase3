# 与 Agent 协作开发

在 NocoBase 3 中，工作流代码由应用 Agent 编写。你负责描述业务、确认方案和风险、验收证据；Agent 负责检查当前应用、实现代码、运行检查并报告结果。

Agent 依靠工作流插件随包发布的 Skill `nocobase-app-plugin-workflow` 完成这些工作。插件安装后，Skill 会同步到应用的 `.agents/skills/`；缺失或过期时，在应用根目录运行：

```bash
pnpm nocobase skills sync
```

`.agents/skills/` 是生成的内容，下一次同步会整体替换，不要直接修改。通常不需要在提示词里点名 Skill：需求涉及多阶段处理、条件路径、后台执行或过程观测时，Agent 会自行读取它。

## 开发流程

| 步骤        | 你要做的                                   | Agent 要做的                                       | 参考                                                                       |
| ----------- | ------------------------------------------ | -------------------------------------------------- | -------------------------------------------------------------------------- |
| 1. 描述需求 | 讲清触发事件、规则、可调配置、副作用和去重 | 检查现有数据结构、Service 和插件，判断是否用工作流 | [提示词手册](./using-skill.md)                                             |
| 2. 确认方案 | 审核流程阶段、输入与参数、副作用边界       | 给出流程结构、职责划分和需要确认的缺口             | [从业务需求到工作流](./design.md)                                          |
| 3. 实现     | 必要时查阅代码                             | 编写 `workflow.ts`、处理函数和测试                 | [工作流定义 DSL](../reference/dsl.md)、[节点](../reference/nodes/index.md) |
| 4. 试跑     | 在 `pnpm dev` 下启用、手动运行、查看记录   | 修复问题，按运行证据诊断                           | [快速开始](../quick-start.md)                                              |
| 5. 接入触发 | 确认由哪个业务操作或定时任务触发           | 接入 Workflow Service 或定时任务，处理重复事件     | [触发与扩展 API](../reference/service-api.md)                              |
| 6. 发布     | 验收检查、测试、构建证据；部署后启用新版本 | 运行完整验证并逐项报告                             | [检查、构建与发布](./verification-and-diagnostics.md)                      |

审阅 Agent 生成的代码时，DSL、节点和触发 API 的细节集中在[参考](../reference/dsl.md)中。

## 三个基本概念

1. 应用 `workflows/` 下的一个目录就是一个工作流，目录名是它的稳定 key；
2. 每次被接受的业务事件产生一条运行记录，固定使用开始时的版本；
3. 工作流只负责编排，具体的数据操作仍由应用的类型化 Service 完成。

## 审核清单

这是 Agent 开发任务的集中审核清单，其他页面只补充各自专题的检查项。

**方案阶段**

- 为什么用工作流（或为什么不用），哪些动作留在 Service 中；
- 节点是否对应有业务意义的阶段，而不是每个查询一个节点；
- 每次运行的输入和管理员参数是否区分清楚，凭证没有放进任何一类；
- 使用的节点类型是否已在应用中注册；需要审批、等待等能力时是否说明了现有能力的限制；
- 会写库、发消息或调用外部系统的节点如何保证幂等，失败后如何重试或补偿。

**交付阶段**

- 实际读取过哪些数据结构、Service 和插件能力；
- 实际运行了哪些命令（workflow check、typecheck、测试、lint、build）及其结果；
- 业务事件如何接入，`skipped` 如何处理；
- 哪些数据库、外部系统或运行时行为尚未验证。

不要把“已经完成”或“代码看起来正确”当作证据。

## 常见问题

### Agent 没有使用工作流

先看它的理由。原子、同步、无需运行记录的操作本来就更适合普通代码。如果业务确实需要持久化过程、路径观测或管理员参数，把这些要求补充进需求，让 Agent 重新判断。

### Agent 使用了应用中不存在的节点

要求 Agent 核对已安装插件的公开导出，并确认源码检查、Artifact 构建和运行时都注册了该节点类型。缺失时应改用已有能力、实现可复用的自定义节点，或重新设计流程，不能仅凭节点名称继续编码。

### Agent 只报告成功，没有给出证据

要求它逐项列出实际执行的命令、退出结果和跳过原因，至少区分 workflow check、处理函数所在应用的类型检查、测试与完整构建。
