# 开发流程

本页面向需要实现自己业务工作流的开发者，按照一次开发的顺序说明每一步要提供什么、如何交给 Agent，以及如何验收。先完成[概览与准备](./index.md)中的准备工作；下面的 `<...>` 是需要替换的内容，示例以库存补货为主。

## 1. 描述需求

先讲清五件事：什么事件触发、业务规则、管理员可调配置、会产生哪些写入或外部调用、重复事件如何处理。不必提前指定目录名、节点 key 或技术方案。

```text
我们的应用需要增加库存补货处理：
- 商品库存发生变化后，在后台判断当前库存是否低于目标库存；
- 目标库存由业务管理员配置，默认 100；
- 库存不足时创建一条补货记录，记录商品、当前库存和需要补充的数量；库存充足时只记录检查结果；
- 管理员要能看到每次处理经过了哪些步骤、结果是什么；
- 同一次库存变化即使被重复通知，也不能重复创建补货记录。
请先整理需求中的规则和待确认问题，暂时不要修改代码。
```

验收时确认：Agent 理解了触发事件、补货条件、参数默认值、写入内容和重复事件规则，并明确列出缺失信息，而不是自行补出业务规则。

## 2. 判断是否需要工作流

需要独立、持久化、可观测的业务生命周期时才使用工作流。一次请求内的查询或计算、必须处于同一事务的原子写入，通常更适合普通业务代码。使用队列、调用多个函数或包含条件分支，本身都不是采用工作流的理由。

```text
请检查当前应用的数据结构、Service 和已安装节点，判断库存补货处理应该使用工作流、普通业务代码还是两者结合。
说明选型理由、可以复用的能力和缺口，暂时不要修改代码。
```

验收时确认：Agent 根据过程观测、后台执行、版本或参数需求说明选型，指出留在 Service 中的动作，并列出实际检查过的数据结构与插件。需要等待或人工审批时，必须先确认已安装能力，不能虚构节点。

## 3. 确认方案

方案应同时说明业务阶段、输入与参数、事件身份和副作用。只有流程图还不足以进入实现。

```text
请给出库存补货的实现方案，包括流程图、每个节点的职责、每次运行的输入、管理员参数、触发事件的稳定身份，以及写入的幂等和失败恢复方式。
指出需要新增或调整的数据表、Service 和节点能力，先给出方案供我确认。
```

### 节点对应业务阶段

合理的拆分是“计算补货缺口 → 判断是否需要补货 → 创建补货记录 / 记录库存充足”。节点内部的查询、计算和写入留在处理函数或 Service 中；不要把“查询一行 → 读取字段 → 相减 → 拼接对象”都拆成节点，也不要把整个多阶段流程塞进一个 Run 模块。

默认节点 Run、Condition 和 Terminate 分别用于业务动作、布尔分支和提前结束。持久等待、人工审批、循环或子流程需要专门的生命周期支持，不能用长时间占用 Worker 的 Run 模块模拟；扩展前应检查实际节点能力，见[自定义节点](../reference/custom-instructions.md)。

### 区分输入与管理员参数

输入随业务事件变化，例如商品 ID 和库存变更版本；管理员参数是部署后可调整的少量配置，例如目标库存。两者在运行开始时形成快照，后续修改不影响已有运行。凭证放在应用配置或秘密管理能力中，不放进输入或参数。

### 确认事件身份和副作用

例如 `stock-changed:<productId>:<revision>` 标识一次已提交的库存变更。重复投递同一事件使用同一个 eventKey，新的变更使用新身份。eventKey 在应用内全局去重，已有失败运行不会因重复触发而重跑。

事件去重不能替代业务幂等。创建补货记录应以库存变更 ID 等业务唯一键约束写入；部分副作用完成后失败，需要判断是否创建新运行或显式补偿。工作流不会自动回滚已经发生的外部副作用。

验收时确认：节点有独立业务意义，输入与参数区分明确，使用的节点实际可用；每个写库、发消息或调用外部系统的动作都有幂等策略和恢复边界，需要新增的数据结构已经确认。

## 4. 实现工作流和业务代码

确认方案后，让 Agent 编写定义、处理函数和相关测试。具体写法见[工作流定义 DSL](../reference/dsl.md)和[节点](../reference/nodes/index.md)。

```text
请按已确认的库存补货方案实现工作流，复用现有 Service，补充库存不足、库存充足和重复事件相关测试。
按应用实际脚本和节点类型执行适用的定义检查、类型检查、相关测试和 lint，逐项报告命令、结果及跳过原因。
提供工作流目录、各节点职责，以及用于试跑的测试数据、输入、预期路径和清理方法。
```

验收时确认：工作流目录和 key 明确，节点说明能让管理员看懂规则和副作用；检查与测试有实际结果，尚未验证的数据库或外部系统行为被明确列出。

## 5. 在开发环境试跑

`pnpm dev` 按需编译工作流源码。保存后刷新管理界面，启用目标版本，再填写参数并手动运行。测试数据应可识别、可清理；手动运行会执行真实业务代码，不是预览。

具体的启用和参数操作见[参数、启停与版本](../management/parameters-and-versions.md)，提交输入的方法见[手动运行工作流](../management/manual-runs.md)。也可以明确授权 Agent：

```text
请在开发环境中启用库存补货处理的<目标版本>，按你提供的测试数据分别运行库存不足和库存充足两个场景。
报告每次运行 ID、实际版本、最终状态、执行路径和节点结果，并核对补货记录。不要操作生产环境。
```

验收时确认：目标库存为 100 时，库存 20 应创建数量为 80 的补货记录，库存 120 不应创建补货记录；每次运行进入终态，路径、节点结果和业务数据都符合预期。提交结果不明确时先查执行记录，不要立即重复提交。

异常诊断见[执行记录与诊断](../management/run-inspection.md#交给-agent-诊断)。诊断与恢复分开，先取证，再确认恢复动作的影响。

## 6. 接入真实触发

编写工作流不会自动监听业务事件。手动试跑通过后，需要把流程接入真实业务操作，或配置定时任务。

### 业务事件触发

```text
请把库存补货处理接入实际的库存变更逻辑。
同一次库存变更重复投递时使用相同的事件标识，处理 accepted 和 skipped 两种结果，补货写入本身也不能重复。
补充测试，并告诉我哪个业务操作会触发它、eventKey 如何构造、触发被跳过时如何处理。不要新增通用的公开触发接口。
```

验收时确认：触发代码所在文件和业务入口、eventKey 构造规则、`skipped` 处理方式，以及重复投递测试的结果。`accepted` 可能对应新运行或已有运行，不代表业务已经成功，最终状态以运行记录为准。API 语义见[触发工作流](../reference/service-api.md)。

### 定时触发

如果业务改为每天检查，可以把调度任务交给 Agent：

```text
请让<工作流的业务名称或目录>每天 <时间>（<时区>）自动执行一次，输入为 <输入内容>。
使用定时任务的内置 workflow 执行目标，同步后告诉我如何在界面中确认执行记录。
```

验收时确认：定时任务 key、Cron、时区、目标工作流和输入正确，报告了同步结果，并能定位定时任务及对应工作流的执行记录。定时任务的操作见[定时任务](../../scheduler.md)。

## 7. 验证并发布

试跑和接入通过后，按[检查、构建与发布](./verification-and-diagnostics.md)完成验证、构建与部署。部署后由管理员确认并启用新版本；部署本身不会自动启用它。

## 修改已有工作流

已有工作流的修改同样要经过影响分析、实现、试跑和发布。先给出业务名称或目录以及新的规则：

```text
将现有<工作流的业务名称或目录>修改为：<新的规则>。
请先找到负责它的工作流和 Service，说明本次修改对输入、参数、节点结果和已发布版本的影响，再修改、测试。
```

验收时确认：Agent 定位的目录正确，说明兼容性影响，提供覆盖变化规则的测试与试跑结果。存在多个相似候选时应先列出供你选择，不要猜测数据库 ID。历史运行保留原版本，部署后需要启用新版本。

## 审核清单

这是 Agent 开发任务的集中审核清单，其他页面只补充各自专题的检查项。

**方案阶段**

- 为什么用工作流（或为什么不用），哪些动作留在 Service 中；
- 节点是否对应有业务意义的阶段，而不是每个查询一个节点；
- 每次运行的输入和管理员参数是否区分清楚，凭证没有放进任何一类；
- 使用的节点类型是否已在应用中注册；需要审批、等待等能力时是否说明了现有能力的限制；
- 会写库、发消息或调用外部系统的节点如何保证幂等，失败后如何重试或补偿。

**交付阶段**

- 实际读取过哪些数据结构、Service 和插件能力；
- 工作流目录、触发入口、测试输入、预期路径与结果，以及试跑的运行 ID；
- 按应用实际脚本和节点类型运行了哪些定义检查、类型检查、相关测试、lint 和 build，各自结果及跳过原因；
- 业务事件如何接入，`skipped` 如何处理；
- 哪些数据库、外部系统或运行时行为尚未验证。

不要把“已经完成”或“代码看起来正确”当作证据。

## 常见问题

### Agent 没有使用工作流

先看它的理由。原子、同步、无需运行记录的操作本来就更适合普通代码。如果业务确实需要持久化过程、路径观测或管理员参数，把这些要求补充进需求，让 Agent 重新判断。

### Agent 使用了应用中不存在的节点

要求 Agent 核对已安装插件的公开导出，并确认源码检查、Artifact 构建和运行时都注册了该节点类型。缺失时应改用已有能力、实现可复用的自定义节点，或重新设计流程，不能仅凭节点名称继续编码。

### Agent 只报告成功，没有给出证据

要求它逐项列出实际执行的命令、退出结果和跳过原因，至少区分 workflow check、处理函数所在应用的类型检查、测试与完整构建。
