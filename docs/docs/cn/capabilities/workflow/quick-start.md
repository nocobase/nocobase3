# 快速开始

本教程用一个库存补货的例子走完最短闭环：把需求交给应用 Agent，在开发环境里启用并手动运行一次，再查看执行记录。全程不需要手写工作流代码。

## 开始之前

- 一个基于 NocoBase 3 模板创建的应用，已安装工作流插件（应用模板默认包含）。还没有应用时，参见[创建应用](../../get-started/create-app.md)；
- 应用目录中已有编码 Agent，例如 Claude Code 或 Codex；
- 应用已用 `pnpm dev` 启动，你能以管理员身份登录。

如果 Agent 找不到工作流 Skill，在应用根目录运行一次：

```bash
pnpm nocobase skills sync
```

:::tip 想先看看工作流长什么样

让 Agent 用 `examples` 模板创建一个示例应用，其中已经带有可以直接运行的工作流，例如“Example: Quotation routing”：进入“设置 → 自动化 → 工作流”，启用后手动运行，输入 `Q-100` 和 `150000`，就能看到分支路径和每个节点的结果。

:::

## 1. 把需求交给 Agent

直接描述业务，不需要指定技术方案，也不需要给工作流或节点起名：

```text
我们的应用需要增加库存补货处理：
- 商品库存发生变化后，在后台判断当前库存是否低于目标库存；
- 目标库存由业务管理员配置，默认 100；
- 库存不足时创建一条补货记录，记录商品、当前库存和需要补充的数量；库存充足时只记录检查结果；
- 管理员要能看到每次处理经过了哪些步骤、结果是什么；
- 同一次库存变化即使被重复通知，也不能重复创建补货记录。

请先检查应用现有的数据结构和 Service，判断是否适合用工作流并说明理由，给出方案后再实现。
```

需求只需讲清五件事：**什么事件触发、业务规则、管理员可调的配置、会产生哪些写入或外部调用、重复事件如何处理**。其余技术规范（检查真实代码、不虚构节点、选择稳定标识、报告验证结果）由 Skill 负责。

## 2. 确认 Agent 的方案

Agent 应先给出类似下面的流程，并说明为什么这里需要工作流（管理员参数、路径观测、重复事件去重）：

```text
计算补货缺口 → 是否需要补货？
                ├─ 是 → 创建补货记录
                └─ 否 → 记录库存充足
```

确认三点即可进入实现：

1. **节点粒度**：节点对应业务阶段，而不是把每个查询都拆成节点；
2. **副作用与幂等**：补货写入是否复用现有 Service，是否有唯一约束或幂等检查；
3. **缺口**：如果应用还没有补货相关的数据表或 Service，Agent 应先说明并与你确认设计。

更完整的审核清单见[与 Agent 协作开发](./development/index.md#审核清单)。

## 3. 在界面中启用

实现完成后，Agent 生成的代码大致是：

```text
workflows/inventory-replenishment/
├── workflow.ts                  # 输入、管理员参数、节点顺序和分支
└── server/
    ├── calculate-shortage.ts    # 各节点的处理函数，调用应用已有的 Service
    ├── needs-replenishment.ts
    ├── create-replenishment.ts
    └── record-stock-sufficient.ts
```

`pnpm dev` 会按需编译工作流源码，不需要构建或重启。刷新管理界面：

1. 进入“设置 → 自动化 → 工作流”，找到“库存补货处理”，此时它是一个未启用的新版本；
2. 打开启用开关；
3. 需要时从“更多操作 → 参数设置”修改目标库存，不修改则使用默认值。

之后再让 Agent 修改这个工作流，会产生新的未启用版本，启用后修改才会生效。

## 4. 手动运行一次

1. 打开工作流详情，从“更多操作”选择“手动运行”；
2. 填写测试商品和当前库存，提交；
3. 页面进入本次执行详情。

:::warning 注意

手动运行会执行真实业务代码，本例会真的创建补货记录。请使用能识别和清理的测试数据；页面暂时没有显示结果时，不要重复提交。

:::

## 5. 查看执行记录

工作流在队列中异步执行，状态会从“排队中”“运行中”变为“已完成”等终态。在执行详情中：

- 流程图会标出本次实际经过的节点，确认“是否需要补货”选择了哪条分支；
- 点击节点查看结果、错误和日志，例如缺口计算得到的数量；
- 核对应用中是否确实生成了对应的补货记录。

所有工作流的运行记录也可以在“自动化 → 工作流执行”中查看，详见[执行记录与诊断](./management/run-inspection.md)。

## 6. 接入真实业务事件

到这里工作流只能手动运行。要让库存变化自动触发它，继续告诉 Agent：

```text
请把库存补货处理接入实际的库存变更逻辑。同一次库存变更重复投递时使用同一个事件标识，补货写入本身也不能重复。
补充测试，并告诉我哪个业务操作会触发它、触发被跳过时如何处理。
```

如果改为每天定时检查，也可以让 Agent 把它配置成定时任务，见[触发与扩展 API](./reference/service-api.md#定时触发)。

## 7. 发布前验证

准备部署时，让 Agent 完成完整验证并逐项报告命令和结果：

```text
请用 Workflow Skill 验证本次修改：运行 workflow check、typecheck、相关测试、lint 和 build，逐项报告命令与结果，并说明哪些运行时行为还没有验证。
```

部署后，新版本同样需要管理员在界面中确认启用，见[参数、启停与版本](./management/parameters-and-versions.md)。

## 常见问题

### 管理界面看不到新工作流

开发环境下先刷新列表，并确认 Agent 把工作流放在应用的 `workflows/` 目录下、`pnpm dev` 仍在运行。生产环境需要重新构建并部署，参见[检查、构建与发布](./development/verification-and-diagnostics.md)。

### 工作流已启用，但业务操作没有触发它

编写工作流并不会自动监听业务事件，需要完成第 6 步的接入。如果已经接入，让 Agent 检查触发结果是否为 `skipped`（工作流不存在或已停用）。

### 重复通知只产生了一次运行

这是预期行为：同一业务事件使用相同的 eventKey 时会被去重。
