# 插件国际化

本页是开发插件的 Agent 的单一 i18n 入口。先用任务表选择路径，再只读取对应章节；不要把 Client locale、Server locale、App 支持语言和语言切换混为一件事。

插件拥有自己的界面文案、API 错误和外发消息翻译。`@nocobase/app-i18n` 提供通用 runtime 和 Client/Server bindings；`@nocobase/app-server-kit` 把 runtime 接入 App Server 的 ServiceContainer。业务插件不负责实现全局语言切换。

## Agent 快速决策

先回答三个问题：

1. 文案在哪里渲染或发送？
2. 文案由 App 还是插件拥有？
3. 当前插件是否已经有对应的 Client/Server entry？

| 任务                            | 修改位置                                | 必须声明或接入                               | 继续阅读                                       |
| ------------------------------- | --------------------------------------- | -------------------------------------------- | ---------------------------------------------- |
| 插件自己的 Route 页面           | `client/locales/`、页面组件             | Client `locales` loader                      | [Client i18n](#client-i18n)                    |
| 插件 Provider 内的组件          | `client/locales/`、Provider/组件        | Client `locales` loader                      | [Client i18n](#client-i18n)                    |
| 插件导出的公共组件              | `client/locales/`、公共组件、exports    | 显式 namespace；必要时 locales-only Client   | [公共组件](#公共组件与-component-only-package) |
| API 响应或请求内 Server 逻辑    | `server/locales/`、Route                | Server `locales` loader                      | [Server i18n](#server-i18n)                    |
| 可重新翻译的 API error          | `server/locales/`、error handler        | `AppI18nError` + `serializeI18nError()` 接线 | [结构化错误](#结构化-api-错误)                 |
| Job、cron、邮件、通知或 webhook | `server/locales/`、dispatcher/Job       | 收件人 locale + 已加载 runtime               | [请求外翻译](#请求外翻译)                      |
| App 自己拥有的页面文案          | App 的 `client/locales/`                | App locale 声明                              | 不修改插件 locale                              |
| 语言选择器或语言持久化          | 目标 App 和 `@nocobase/app-plugin-i18n` | 使用现有切换能力                             | [语言切换的所有权](#语言切换的所有权)          |

### 按任务读取

```text
普通 Client 页面/Provider
→ 共享规则 → Client i18n → Client 测试

Server API/同步请求
→ 共享规则 → Server i18n → 请求测试

Job/邮件/通知/webhook
→ 共享规则 → 请求外翻译 → 非默认语言测试
```

## 共享规则

### 文案所有权

```text
插件拥有的文案 → 插件自己的 locales/ 和 packageName namespace
App 拥有的文案 → App 的 client/locales/ 和 App namespace
```

不要因为组件源码位于插件目录，就把 App-owned 文案放进插件。也不要让插件修改目标 App 的 locale 文件来“补齐”自己的资源。

### Namespace 等于 package name

插件 namespace 固定使用 `package.json#name`，也是 `defineClientPlugin()` 和 `defineServerPlugin()` 中的 `packageName`。Client 和 Server 必须使用同一个值：

```ts
import type { Namespace } from '@nocobase/app-i18n';

export const AUDIT_LOG_NS: Namespace = '@nocobase/app-plugin-audit-log';
```

不要另造短 namespace，也不要把某个目标 App 的 package name 写进插件。key 的 fallback 顺序是：

```text
当前插件 namespace → 目标 App namespace → @nocobase/app-i18n
```

### Locale 文件和类型

每一侧都是独立 TypeScript module；不要让 Client import `server/locales/`，也不要让 Server import `client/locales/`。

```text
client/locales/              server/locales/
├── index.ts                 ├── index.ts
├── en-US.ts                 ├── en-US.ts
└── zh-CN.ts                 └── zh-CN.ts
```

`en-US.ts` 是 key 结构的 source of truth：

```ts
// locales/en-US.ts
import type { LocaleResource } from '@nocobase/app-i18n';

const enUS = {
  nav: { title: 'Audit logs' },
  errors: { notFound: 'Audit log {{id}} was not found' },
};

export type AuditLogResource = LocaleResource<typeof enUS>;
export default enUS;
```

```ts
// locales/zh-CN.ts
import type { AuditLogResource } from './en-US.js';

const zhCN: AuditLogResource = {
  nav: { title: '审计日志' },
  errors: { notFound: '未找到审计日志 {{id}}' },
};

export default zhCN;
```

key 表达稳定语义，不直接使用英文句子或动态 ID。动态值使用插值：

```ts
t('errors.notFound', { id });
```

只有在明确允许暂时不完整时才使用 `PartialLocaleResource`。缺 key 会 fallback，不代表翻译已经完成。

每种语言在 `index.ts` 中使用一个 dynamic import：

```ts
import type { LocaleLoaders } from '@nocobase/app-i18n';

const locales: LocaleLoaders = {
  'en-US': () => import('./en-US.js'),
  'zh-CN': () => import('./zh-CN.js'),
};

export default locales;
```

不要用字面量调用某个 loader（例如 `locales['en-US']()`）来预加载资源；语言应由 runtime 值选择，以保留 lazy loading。

### Plugin resources 不等于 App supported locales

| 层级                        | 决定什么                                   |
| --------------------------- | ------------------------------------------ |
| 插件 `locales/index.ts`     | 当前 namespace 能提供哪些 locale resources |
| App i18n config             | App 能解析和使用哪些 locale                |
| `@nocobase/app-plugin-i18n` | 用户如何查看、切换和持久化 locale          |
| Runtime fallback            | 当前 namespace 缺少 locale 或 key 时用什么 |

插件声明 `zh-CN` 不会自动把 `zh-CN` 加入 App 的语言选择器；App 支持 `zh-CN` 也不保证每个插件都已翻译该语言。

## Client i18n

### Client 最小文件闭环

一个插件页面需要的最小路径是：

```text
client/plugin.ts
→ client/locales/index.ts
→ client/locales/en-US.ts + zh-CN.ts
→ client/pages/audit-log-page.tsx
→ target App client/plugins.ts
```

新插件显式选择 `client.locales`：

```bash
pnpm plugin:create audit-log --with client.locales
```

它会生成最小 `client/locales/`、`client/plugin.ts` 和 `./client` exports。`client.routes`、`client.providers` 或 `client.bootstrap` 不会隐式生成翻译资源；需要页面和翻译时同时选择两个 capability。修改已有插件时，手动保持资源、`locales` loader、exports 和 `@nocobase/app-i18n` 依赖一致。

### 声明 Client resources

```ts
import {
  defineClientPlugin,
  type AppClientPluginFactory,
} from '@nocobase/app-client/plugins';

const auditLog: AppClientPluginFactory = defineClientPlugin({
  packageName: '@nocobase/app-plugin-audit-log',
  locales: () => import('./locales/index.js'),
  routes: () => import('./routes.js'),
});

export default auditLog;
```

`locales` 是资源声明，不是 UI contribution。Client runtime contribution 仍只有 `bootstrap`、`routes` 和 `providers`，全部可选。

### 在页面或 Provider 中使用

插件自己的 Route 或 Provider render tree 会根据 contribution `packageName` 提供默认 namespace：

```tsx
import { useTranslation } from '@nocobase/app-i18n/client';
import type { ReactElement } from 'react';

export default function AuditLogPage(): ReactElement {
  const { t } = useTranslation();
  return <h1>{t('nav.title')}</h1>;
}
```

使用 `@nocobase/app-i18n/client` 的 binding，不要从 `react-i18next` 建立插件级约定。focused test 没有挂载 `I18nProvider` 时，必须保持可读的字符串应传 `defaultValue`；只调用 `t('nav.title')` 可能渲染 key：

```tsx
t('nav.title', { defaultValue: 'Audit logs' });
```

## Server i18n

新插件显式选择 `server.locales`：

```bash
pnpm plugin:create audit-log --with server.locales
```

它会生成独立的 `server/locales/`、Server plugin declaration 和所需依赖。Client 和 Server 同时需要翻译时分别选择 `client.locales` 与 `server.locales`，不要跨运行时复用 locale module。

### Server 最小文件闭环

```text
server/plugin.ts
→ server/locales/index.ts
→ server/locales/en-US.ts + zh-CN.ts
→ server/routes/index.ts 或 Service
→ target App server/plugins.ts
```

### 声明 Server resources

```ts
import {
  defineServerPlugin,
  type AppServerPlugin,
} from '@nocobase/app-server-kit/plugins';

const auditLogPlugin: AppServerPlugin = defineServerPlugin({
  packageName: '@nocobase/app-plugin-audit-log',
  locales: () => import('./locales/index.js'),
});

export default auditLogPlugin;
```

### 请求内翻译

App Server 的 i18n middleware 按以下顺序解析请求语言：

```text
session 中保存的语言 → Accept-Language → App 默认语言
```

它会在 Route 执行前加载资源。使用 `getRequestTranslator()` 获取请求 translator，并显式绑定插件 namespace：

```ts
import { getRequestTranslator } from '@nocobase/app-i18n/server';

router.get('/audit-logs/:id', async (context) => {
  const t = getRequestTranslator(context, AUDIT_LOG_NS);
  const id = context.req.param('id');
  const record = await findAuditLog(id);

  if (!record) {
    return context.json({ message: t('errors.notFound', { id }) }, 404);
  }

  return context.json(record);
});
```

`getRequestTranslator(context)` 省略 namespace 时默认使用 App namespace；插件 Route 不要假设“代码属于插件”会自动改变 Hono context 的 namespace。如果 middleware 没有在 Route 前运行，accessor 会抛出接线错误，这应在目标 App integration test 中被发现。

领域 Service 通常不读取 Hono context，也不应在抛错时提前选择请求语言。由 Route 在 HTTP 边界翻译普通响应；需要跨边界保留翻译信息时，Service 抛出下面介绍的结构化错误。

### `i18nToken` 与通用 i18n API 的边界

`i18nToken` 不是 `@nocobase/app-i18n` 的通用 API，而是 NocoBase App Server 的 ServiceContainer token：

```ts
import { i18nToken } from '@nocobase/app-server-kit/i18n';

const i18n = app.container.resolve(i18nToken);
```

它定义在 `packages/app-server-kit/src/i18n/index.ts`，由 `I18nProvider` 创建并注册 `I18nRuntime`。使用场景是 Provider、dispatcher 或其他拥有 App container 的 Server 集成代码。

当前 source workspace 已导出 `@nocobase/app-server-kit/i18n`，但使用它编写可发布插件前，还必须确认 `@nocobase/app-server-kit` 的 `publishConfig.exports["./i18n"]` 已同步存在。source export 和 publish export 不一致时，不要把这个 subpath 当作发布契约；先补齐拥有包的发布导出并验证 tarball。

```text
请求 Route + Hono context
→ @nocobase/app-i18n/server → getRequestTranslator()

App Server Provider/dispatcher + container
→ @nocobase/app-server-kit/i18n → i18nToken

默认 Queue Job
→ 没有 ServiceContainer，不能直接 resolve i18nToken
```

## 高级场景

### 公共组件与 component-only package

namespace scope 跟随 React render tree，不跟随源码所有权。插件导出的公共组件被 App 页面或其他插件渲染时，必须显式绑定：

```tsx
import { useTranslation } from '@nocobase/app-i18n/client';
import type { ReactElement } from 'react';

export function AuditSummary(): ReactElement {
  const { t } = useTranslation(AUDIT_LOG_NS);
  return <span>{t('nav.title')}</span>;
}
```

也可以使用 `withNamespace(AUDIT_LOG_NS, Component)`。显式绑定只选择 namespace，不会注册 resources。

只提供公共 component subpath、没有 `./client` runtime entry 时，选择以下一种所有权：

```text
文案归 App
→ App 传入 label，或由 App wrapper 使用 App locales 翻译

文案归插件
→ 增加只含 packageName + locales 的 Client factory
→ 增加 ./client source/publish exports 和 app-i18n 依赖
→ 由目标 App 显式注册该 factory
```

不要为了注册 locale 伪造空 Route 或 Provider，也不要假设 component export 会自动注册 namespace。

### 结构化 API 错误

只有在需要稳定 error code，或 Client 需要按当前 UI 语言重新翻译时，才使用 `AppI18nError`：

```ts
import { AppI18nError } from '@nocobase/app-i18n/server';

throw new AppI18nError('AUDIT_LOG_NOT_FOUND', {
  status: 404,
  ns: AUDIT_LOG_NS,
  key: 'errors.notFound',
  params: { id },
});
```

它只是可翻译的数据载体，不会自动安装 HTTP error handler。完整闭环必须是：

```text
Route/Service throws AppI18nError
→ App/Route HTTP error handler catches it
→ serializeI18nError(runtime, error, requestLocale)
→ response contains code, message, ns, key, params
```

Route contribution 可以在自己拥有的 router 边界完成序列化：

```ts
import {
  getRequestLocale,
  isAppI18nError,
  serializeI18nError,
} from '@nocobase/app-i18n/server';
import { i18nToken } from '@nocobase/app-server-kit/i18n';
import type { AppPluginApplication } from '@nocobase/app-server-kit/plugins';
import {
  defineApiRoutes,
  type AppApiRouteContribution,
} from '@nocobase/app-server-kit/router';
import { Hono } from 'hono';

export const apiRoutes: AppApiRouteContribution<AppPluginApplication> =
  defineApiRoutes(({ container }) => {
    const router = new Hono();
    const i18n = container.resolve(i18nToken);

    router.onError((error, context) => {
      if (!isAppI18nError(error)) throw error;

      return new Response(
        JSON.stringify({
          error: serializeI18nError(i18n, error, getRequestLocale(context)),
        }),
        {
          status: error.status,
          headers: { 'content-type': 'application/json; charset=UTF-8' },
        },
      );
    });

    // Register this plugin's authenticated and authorized routes here.
    return router;
  });
```

示例省略了业务 Route，但生产 contribution 仍必须安装并测试自己的 authentication/authorization。若插件不准备依赖 `i18nToken` 的发布 subpath，就由目标 App 拥有等价的全局 HTTP error handler，并将结构化错误响应视为 App 集成契约。

`message` 供纯 API 客户端直接显示；`code/ns/key/params` 供 Client 重新翻译。错误序列化不替代 Route 自己的 authentication/authorization 边界。

### 请求外翻译

Job、cron、邮件、通知和 webhook 没有 request locale。外发语言属于收件人，不属于触发任务的操作者：

```ts
const locale = recipient.appLang;

await i18n.ensureLocaleLoaded(locale);
const t = i18n.getFixedT(AUDIT_LOG_NS, locale);

await sendMail(recipient.email, {
  subject: t('mail.reportReady'),
});
```

`getFixedT()` 参数顺序是 `namespace, locale`；必须先 `ensureLocaleLoaded()`，否则可能静默 fallback。多个收件人应分别选择语言。

默认 Queue Job 没有 `ServiceContainer`，不能在 handler 中假设存在 `container` 或全局 `i18n`。推荐：

```text
Provider/dispatcher 拥有 container
→ resolve(i18nToken)
→ 按收件人 locale 加载并翻译，或建立明确 translation adapter
→ 派发 Job / 调用外发服务
```

如果必须在 Job 内翻译，插件需要设计显式 adapter/dispatcher 契约，并为该依赖做目标 App integration test。

### App 覆盖插件措辞

目标 App 可以在自己的 locale resource 中覆盖插件 key，而不修改插件源码：

```ts
// target-app/client/locales/zh-CN.ts
export default {
  overrides: {
    '@nocobase/app-plugin-audit-log': {
      nav: { title: '操作记录' },
    },
  },
};
```

覆盖内容归 App 所有，只用于产品措辞差异；插件缺少 key 或语言时仍应修复插件自己的 source resources，不能把 App override 当成插件翻译补丁。

## 语言切换的所有权

普通业务插件只声明自己能提供哪些 locale resources，并随 runtime 的语言变化重新渲染。不要重新实现：

- locale picker 或 `LanguageSwitcher`；
- 用户语言持久化；
- `GET /api/i18n/locales` 和 `POST /api/i18n/locale`；
- 全局 language change、`html lang` 或 `dir` 同步。

这些能力属于 `@nocobase/app-plugin-i18n`。插件 resource 列表和 App 支持语言列表仍需分别配置。

## 测试、构建与发布

按层验证，不要用单个 Inspector 代替行为测试：

### 1. Locale 结构

```bash
pnpm i18n:check
pnpm i18n:check --strict
```

默认命令报告缺失 key 但不失败；完成检查或 CI 使用 `--strict`。该命令只检查 `packages/` 下 locale 文件的 key 结构，不证明 namespace 注册、fallback、语言切换、请求语言或 lazy loading。

### 2. 插件包

```bash
pnpm --filter <plugin-package> typecheck
pnpm --filter <plugin-package> test
pnpm --filter <plugin-package> build
```

覆盖至少：`en-US` source shape、其他语言、Client 双语言渲染、Server 请求 locale、结构化 error 或请求外收件人 locale（按实际变化选择）。

### 3. 目标 App

```bash
pnpm --filter <target-app> typecheck
pnpm --filter <target-app> test
pnpm --filter <target-app> build
```

注册或 composition 变化时，再运行对应的 `client:inspect` 或 `server:inspect`；它们静态报告 locales loader 是否进入最终装配，但不会执行 loader、展开 locale keys 或验证翻译行为。Client 可用 `client:inspect --type locales --json` 只读取 locale declaration 摘要。

### 4. 发布和运行时

- 插件 package build：确认每个 locale module 都被编译并进入发布 tarball；
- 目标 App Client build：确认语言 dynamic import 保留为可加载的 lazy chunk；
- Server build：确认 locale module 可以从 `dist` 动态解析；
- 启用 `@nocobase/app-plugin-i18n` 时，切换至少两种语言并观察真实文本；
- 请求外消息使用非默认收件人语言；
- 结构化 error 经目标 App HTTP error handler 输出稳定字段。

## 不要这样做

- 使用 `--with client.locales` 或 `--with server.locales`，不创建笼统的 `--with i18n` capability；
- 不让 Client 和 Server 共用对方的 locale module；
- 不创建任意短 namespace；
- 不把 namespace 写成目标 App 的 package name；
- 不从 `react-i18next` 建立插件公共约定；
- 不假设公共组件会自动注册 namespace resources；
- 不假设 Job 有 request locale、ServiceContainer 或全局 `i18n`；
- 不把触发者语言用于所有收件人；
- 不只构造 `AppI18nError` 而跳过 HTTP serialization；
- 不用 `inspect` 验证 locale keys 或翻译行为；
- 不把插件 resource 列表当成 App supported locales；
- 不把 fallback 当成翻译完成；
- 不把 dynamic import 改成启动时加载所有语言。

## Agent 完成检查

- [ ] 文案所有权已明确，App-owned 和 Plugin-owned 没有混用；
- [ ] namespace 与插件 `packageName` 完全一致；
- [ ] 只修改了实际使用翻译的一侧 locale resources；
- [ ] `en-US` 定义结构，其他语言通过 `LocaleResource` 对齐；
- [ ] `locales` loader 已在正确的 Client/Server plugin declaration 中声明；
- [ ] Client 页面使用 scoped namespace，公共组件显式绑定 namespace；
- [ ] 请求内翻译使用 request translator，请求外翻译使用收件人 locale；
- [ ] 需要时先 `ensureLocaleLoaded()`，没有把 `i18nToken` 误用于默认 Job；
- [ ] 结构化错误有目标 App HTTP error handler 接线；
